# TMO-060 交付報告：`--batch-limit`（批次上限正名）＋預設不再丟檔

- 日期：2026-10-05｜Story Point：3｜優先級：P3
- 目標檔：`skills/dav-wiki/scripts/wiki-media-describe.sh`
- 相關：TMO-058（同家族「不得假成功」，本票由其收尾揭露）
- 狀態：Gate 1/2/3 全綠；**Gate 4 Round-1 = `request-changes`（1 P1／4 P2／8 P3）→ 全部處置完成 → Round-2 見 §7**

## 1. 問題（本來有多嚴重）

| # | 事實 | 影響 |
|---|---|---|
| 1 | 預設 `MAX_CONCURRENCY=4`，而 `process_batch` 是 `if [[ $ok -ge $MAX_CONCURRENCY ]]; then …` | **預設就會丟檔**：任何 >4 檔的批次，第 5 檔起不處理（TMO-058 後至少會 WARN，之前是靜默丟） |
| 2 | 旗標名叫 `--max-concurrency`、usage 寫「平行處裡數」（還錯字） | **名實不符**：實作是逐檔同步迴圈，完全沒有並發 |
| 3 | 額度計的是**成功數** | `--max-concurrency 1` 遇 1 個失敗時，實際會處理 2 檔 |
| 4 | 不符 mode 白名單的檔在批次模式**完全靜默**（單檔模式早有 WARN） | 使用者以為處理了，其實沒處理 |
| 5 | 批次 dry-run 仍印 `✅ 批次完成：N 個檔案` | 沒真的做事卻宣稱完成 |

## 2. 決策（§2.1，用戶選 A）

正名為「單次批次上限」，**不做**真並發（real API 尚未接上、無收益、且 `wait -n` 需 bash 4.3+ 會撞 macOS 3.2 相容）。

## 3. 契約（前 → 後）

| 情境 | 舊 | 新 |
|---|---|---|
| 預設值 | `4`（>4 檔批次會丟檔） | **`0`＝無限制** |
| 旗標名 | `--max-concurrency`（宣稱平行度） | **`--batch-limit`（正名）**；`--max-concurrency` 保留為**等價別名** |
| 語意 | 最多**成功** N 檔 | 最多**嘗試** N 檔（失敗檔也佔額度） |
| 非法值 | `0` 非法（零產出卻印 ✅ 回 0）；`2x` 默默不限制 | `-1`／`2x`／`1.5`／`007` → `ERROR: --batch-limit 需為 0 或正整數（不得有前導零）（收到：…）` rc `1`（訊息用**實際旗標名**）。**拒收前導零是刻意的**：放行 `007` 就得放行 `08`／`09`，會進 `[[ $N -gt 0 ]]` 的八進位算術 → `value too great for base` |
| 缺值 | `set -u` 下 `unbound variable` 中止（無訊息） | 走同一條友善錯誤（`${2:-}`）rc `1` |
| 截斷 | `⚠ 已達 --max-concurrency 上限（N），尚有 K 個未處理`（rc 0） | `⚠ 已達 <使用者實際打的旗標> 上限（N），尚有 K 個未處理`（rc 0） |
| 白名單略過 | 完全靜默 | `⚠ 已略過 K 個不符 <mode> 白名單的檔`（rc 0） |
| **全數**被略過 | 靜默 + `✅ 批次完成：0 個檔案` | **明示契約**：WARN 計數 + `✅ 批次完成：0 個檔案`、rc 0（「成功」＝沒有失敗，不是有產出；由 AC-D35 鎖住） |
| 隱藏檔 | `find -iname` 會連 `._IMG.JPG`（AppleDouble）一起處理 | 只有「**隱藏且**不符白名單」才不計不報（`.DS_Store`）；`.cover.png` 這種**合法**隱藏媒體檔仍處理（AC-D37） |
| 副檔名大小寫 | `find -iname`＝**不敏感**（`IMG_001.JPG` 會處理） | 維持不敏感（`grep -qiE`；Round-1 P1-1 回歸鎖 AC-D34） |
| 單檔模式大小寫 | 不敏感度不一致：大寫會 WARN「not an image file」卻照做 | 統一 `-qi`：大寫不再誤報 WARN（AC-D36） |
| dry-run | `✅ 批次完成：N 個檔案` | `[DRY-RUN] 批次完成：N 個檔案` |
| 空目錄 | `✅ 批次完成：0 個檔案` | 不變（真的沒有檔要處理＝成功） |
| rc 碼 | `0/1/2/3/5/6` | **完全不變** |

> **rc 完全不變**是本票刻意的約束：TMO-058 剛把 rc 契約鎖好，本票只改「旗標語意＋訊息誠實度」。

### 事故（誠實記錄）

1. **多檔編輯是原子性的**：第一次用一個 edit 呼叫送 7 處修改，其中 1 處 oldText 不匹配 → 整個呼叫失敗，**7 處全部沒套用**。
   我卻先跑了測試、看到 D31 仍紅，以為「邏輯寫錯」；重跑舊碼才發現是**編輯沒生效**（輸出還是 `上限（4）` 這種舊訊息）。
   → 教訓：編輯失敗要當「完全沒改」處理；用「舊訊息是否還在」當第一道自檢。
2. **M21 一開始不咬**：我以為「D29 已斷言 `需為 0 或正整數`」就有鑑別力，實測發現把訊息寫死成 `--batch-limit` 的突變**全綠存活**
   → 已把 D29 收緊到整行（含實際旗標名），重測才咬住。這條是 reviewer P3-1 的價值：**P3 也能是「探針有洞」的通知**。
3. **ENV-EQ-17 由 Gate 2 擋下**：`（收到：$n）` 讓 `$n` 緊接非 ASCII → `lint-shell-var-nonascii.py` **FAIL**，Gate 3 也出現 1 條 `not ok`。
   改成 `${n}` 後全綠。這正是那道鎖存在的理由（本機常綠、CI／bash 3.2 才炸的類型）。
4. **Round-2 又抓到「看似有斷言、實則無鑑別力」的第二例**（P2-1 的 M15）：我寫的 M15 描述沒說出實際 regex，
   於是「只擋非數字」那種讀法下 D29 其實**不會紅**——我引用它當 AC-D29 放寬的補償證據，等於拿一個未經區分的實驗當證詞。
