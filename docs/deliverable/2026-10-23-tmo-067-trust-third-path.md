## 1. 為什麼做這個改動

dav-trust v2.3 已把 trust 定位為「執行模式」（§2.3 → §2.5）。但 agent 的第一份文件是 `AGENTS.md`，
而它寫著「**開發編程任務 → 一律走完整 SOP（§2.1 → §2.5），不開例外**」—— trust 的典型任務（跑 CRM、
做會員系統）**就是**開發任務。兩句話對同一件事給出互斥指令，agent 會先命中前者。

**風險不是抽象的**：在 trust 內跑 §2.1（多輪提問）或 §2.2（用戶簽核）＝ 違反 trust 的「中途不問用戶」
＝ 與 v2.3 修掉的「啟動即注定卡死」同一類死鎖，只是換了位置。

## 6. 反思

**這次最該記錄的一件事：例外要寫在「會被讀到的那一段」，不是寫在檔頭。**

第 2 輪我以為在 §2.4 檔頭加一條例外就收工了，第 3 輪 reviewer 指出：§2.4 的**判定條款**
（通過條件 5、「假裝通過」❌ 清單）與 dav-reflection 的 Step 5 動作/產出/證據都是「無條件語氣」，
agent 判 gate 過不過時看的是它們，不是檔頭的說明。依字面讀 → 判定「假裝通過」→ 依 §2.7 必須停下回報
→ 又是死鎖。**檔頭例外 ≠ 覆蓋範圍**；真正有效的是「就地例外 + 優先序條款」。

**第二件事：探針的「會咬」不能只靠推演。** 第 3 輪前我自己跑突變實測，發現探針 9 是**假綠**
（刪掉「一般任務」列它仍綠，因為 §2.x 索引表也有同樣字串）。若沒實測，這個假綠會跟著上版。
之後我把探針改成「§2.0 章節內取列 + 取指定欄」，並附三種突變的實測證據 —— 探針的價值在於
**有人（或我）故意破壞它時會叫**，不在於現在全綠。

**第三件事：越修越覺得「登錄一條路徑」比「加一個例外」更誠實。** trust 不是一般任務的例外，
它有自己���入口條件（大目標 + deadline + 既有 backlog / 設計），分類維度不同；寫成第三條路徑，
agent 才有機會在**分類階段**就判對，而不是在執行到一半才發現走錯分支。

**第四件事：三輪二審的成本是真的值得的。** 每一輪都抓到我用「看起來合理」的寫法留下的真死鎖
（§2.0 的「不開例外」→ §2.3 的 ask_user → §2.4 的假裝通過條款）—— 這三個是同一個 bug 的三層皮，
我只補了第一層就以為補完了。若沒有逐輪二審，這份 SOP 現在會是「看起來登錄了、實際仍會卡死」的狀態。
