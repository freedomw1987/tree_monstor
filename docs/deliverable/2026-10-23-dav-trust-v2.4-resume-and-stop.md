## 1. 為什麼做這個改動

trust 是**長時程**任務，最容易壞掉的不是做錯，而是**中途中斷**：

| 中斷型態 | 沒機制時的後果 |
|---------|--------------|
| session 中斷 / 崩潰 | 不知道 deadline 還剩多少 → 要嘛超時、要嘛白做 |
| context 壓縮 | 忘記 START_TS / DEADLINE_TS / 已完成到哪 → 從頭再來 |
| 使用者叫停 | 不知道「停下要做什麼」→ 半成品留在工作區、無交付摘要 |

**核心設計**：把 trust 的狀態**外化到檔案**（trust-log 檔頭 = checkpoint）—— 中斷後不需要「記得」，只需要「讀得到」。

## 6. 反思

**第一件事：守護探針「看起來在」可能等於「不在」。**
這次最有價值的發現不是續跑機制本身，而是：那條「主檔變動歷史 ≤3 條」的探針**從來沒跑過** ——
因為測名含中文，在本機 bash 3.2 下被 bats 靜默丟棄（`declared == planned` 仍相等，因為 bats 的 --count
也用同一套解析器，所以連 ENV-EQ-9 的 census 都抓不到）。它還剛好是我唯一會擋下「4 列」的守護。
**如果沒有 reviewer 指出 P0，我會帶著一個從未生效的守護 + 一份「25/25 全綠」回報交付。**
真正的教訓是：**「探針全綠」這句話本身需要證據**（declared == executed、mutant 會死），
否則它只是「沒有人反對」。

**第二件事：mutant 是唯一能證明「守護會咬」的機制。**
我加的 3 支 mutant 立刻抓到兩個「探針咬不住」：DT-M2 第一次只斷言「進度錨點」四字（同一行後段還有該字串 → 活著）、
DT-M3 只斷言主檔含「進度錨點」（變動歷史列餵飽 → 活著）。兩次都是「探針存在但形同虛設」。
**先寫 mutant 再信探針**，比事後補探針有效得多。

**第三件事：`-f` 過濾器把測名當 regex 這件事，會讓「探針存在」也變得可疑。**
測名含 `+` → `bats -f` 匹配不到 → mutant runner 以為探針壞了。已把含 `+` 的測名改成 `and`
（含 restruct-agents-md.bats 2 個）。這是「命名規範」比「測試內容」更早影響可運作性的例子。

**第四件事：語意必須全檔一致，「一個詞兩個定義」比漏寫更危險。**
「停」在主檔＝結束、在 resume.md＝暫停 —— 同一個 token 兩種行為，agent 只讀入口檔就會做錯。
第 2 輪 reviewer 抓到後才發現 §4.2 的 7 步序列對兩種語意**完全相同**（都輸出 🏁、都退出身份），
我原本寫的「暫停＝保留身份」根本沒實作到。**分流的差別要落在「輸出什麼 + 退出與否」，不是只寫在說明裡。**

**第五件事：敘事也要過審。**
我在 CHANGELOG 寫「bats 1.14 會丟 CJK 測名」，reviewer 指出 repo 自證相反（ENV-EQ-9 的 canary 記載
「bats 1.14.0 會跑 CJK 名」）—— 真正的根因是 **bash 3.2 + UTF-8**（本機），CI 的 bash 5.x 正常。
寫錯根因會誤導後人去改上百支測名。**「我觀察到的現象」與「機制的真實原因」要分開寫。**
