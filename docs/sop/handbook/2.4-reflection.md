# §2.4 自我反省（開發編程任務）

> 本檔是 SOP §2.4 的詳細內容（AGENTS.md 自 2026-10-26 起不再內嵌 SOP；本節的規則本體以本檔為準）。引用：`[§2.4](./sop/handbook/2.4-reflection.md)`
>
> ⚠️ **例外：trust mode 進行中** —— 本節的「用戶參與確認」（Sprint / Module 級別必須有用戶參與）
> **不適用**：trust 內不得中途停下問用戶。
> **本例外效力大於本節下方所有內文條款**（含通過條件與「假裝通過」清單）—— gates.json 與本檔以預設策略為準，
> trust 例外以本節為準。
> ① Sprint / Module 級反省由 Agent 自動完成並寫入 deliverable 的「## 反思」末段；
> ② 需用戶決策的事項改寫進 need-you-help 檔，交由用戶在 trust 結束後逐題回覆（見同套 dav-trust skill，需同套安裝）；
> ③ Action Items 一律寫進 backlog，不停在對話等確認。

對執行階段得出的結果作一個宏觀的反思和檢討，包括 UX/UI 是否符合用戶需求原意、RWD 是否有考慮和完成、系統是否有技術債等問題，這個階段看整體，也要看和更改 `docs/backlog.md`；

> ⚠️ **前置條件（v2.2 新增）**：進入本節前必須已過 **§2.3 尾段的 Gate 4.5 需求對帳**。
> 對帳是「事實比對」（需求句 ↔ 成果），反省是「觀點評析」（做得對不對）——順序反了會讓反省
> 建立在未經驗證的「已完成」前提上，把落差洗成「已反思」。
> 對帳未全數對上時：反省只能記錄缺口，**不得**把未完成項當成已完成來反省；
> 交付狀態同時受硬門檻約束（不得標「✅ 完成」）。詳見同套 §2.3 檔案的 Gate 4.5 段落。

**務必使用 `/skill:dav-submitter` 技能**（v2.6 起反省併入提交 skill：Step 3.5 反省）；

## 觸發時機（三層級）

- **User Story 級別**：每個 US 完成驗收後進行輕量反省，Agent 自動執行
- **Sprint 級別**：每個 Sprint 結束後進行標準反省，Agent + 用戶共同檢視（trust mode 進行中：Agent 自動完成 + 待決事項寫 need-you-help 檔）
- **Module 級別**：每個功能模組交付後進行深度反省，Agent + 用戶共同檢視（trust mode 進行中：Agent 自動完成 + 待決事項寫 need-you-help 檔）

## 6 項必檢查維度

1. **UX/UI 一致性** — 是否符合用戶需求原意、符合 docs/DESIGN.md
2. **RWD 響應式設計** — 桌面、平板、手機是否正確呈現
3. **技術債** — 硬編碼、缺少抽象、文件缺失、過時依賴
4. **可維護性** — 代碼結構、命名、模組化、重複代碼
5. **測試覆蓋率** — AC 對應測試、回歸測試
6. **需求對齊** — 實際交付是否滿足用戶痛點和目的

## 關鍵原則

- 看整體：不要只看單一檔案，要從模組、Sprint 級別看全局
- 誠實面對問題：找到問題不要迴避，要明確標記 ❌
- 轉化為行動：反省的目的不是抱怨，而是產出可執行的 Action Items
- 用戶參與：Sprint 和 Module 級別的反省必須有用戶參與確認（**trust mode 進行中除外**）

## fail-fast Reflection Gate — 反省 + backlog 更新 gate（必須通過才能進入 §2.5）

- **觸發**：`/skill:dav-submitter`（Step 3.5 反省：產出 6 維度反省段；**v2.0：併入 §2.5 deliverable.md 末段「## 反思」**）

```markdown

**日期**：YYYY-MM-DD
**Backlog**：<相關 US / DE / TECH ID>
**層級**：User Story / Sprint / Module

## 6 維度檢查

| # | 維度       | 結果    | 備註 |
| - | -------- | ----- | -- |
| 1 | UX/UI 一致性 | ✅/⚠️/❌ |    |
| 2 | RWD 響應式設計 | ✅/⚠️/❌ |    |
| 3 | 技術債      | ✅/⚠️/❌ |    |
| 4 | 可維護性     | ✅/⚠️/❌ |    |
| 5 | 測試覆蓋率   | ✅/⚠️/❌ |    |
| 6 | 需求對齊     | ✅/⚠️/❌ |    |

## 問題清單（V15 — 每個 ❌ 必含「根因 + 建議」）

- ❌ [P1] <問題描述> — 根因：... — 建議：...
- ❌ [P2] <問題描述> — 根因：... — 建議：...

## Action Items（V15 — 必含 4 欄位）

| # | 動作 | 類型（TECH/DE/US/Spike） | 驗收條件 | 預估 |
| - | -- | ----------------- | ---- | -- |
| 1 |    |                   |      |    |
```

### 通過條件

1. **反思併進 `docs/deliverable/<YYYY-MM-DD>-<task-slug>.md` 末段**「## 反思」（v2.0 新；不再獨立成檔）
2. 每個 ❌ 都有「**根因 + 建議**」（V15 — 可執行性）
3. 每個 Action Item 都填滿「**動作 + 類型 + 驗收條件 + 預估**」（V15）
4. **更新 `docs/backlog.md`** — 把問題清單轉化為：
   - 技術債問題 → Technical Debt（TECH）
   - Bug → Defects（DE）
   - 缺失功能 → User Story（US）
   - 需研究 → Spike
5. **用戶參與確認**（Sprint / Module 級別必參與；US 級別可 Agent 自動；**trust mode 進行中：由 Agent 自動完成 + 待決事項寫 need-you-help 檔，視為通過**）

### 「假裝通過」視為失敗（見 [§2.7](./2.7-violations.md)）

- ❌ 交付 deliverable.md 但沒反思末段
- ❌ 更新 `docs/backlog.md` 但 deliverable.md 沒對應的 Action Items
- ❌ Action Items 缺少「驗收條件」或「預估」（V15）
- ❌ 問題清單的 ❌ 沒有「根因 + 建議」（V15）
- ❌ Sprint / Module 級別沒有用戶參與確認（trust mode 進行中除外）
