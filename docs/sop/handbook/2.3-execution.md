# §2.3 執行（開發編程任務）

> 本檔是 SOP §2.3 的詳細內容（AGENTS.md 自 2026-10-26 起不再內嵌 SOP；本節的規則本體以本檔為準）。引用：`[§2.3](./sop/handbook/2.3-execution.md)`
>
> 四道大 Gate 的**定義**自 2026-10-26 起由各自承載它的 skill 負責：
> gate-1/2 → `dav-developer`、gate-3 → `dav-developer`、gate-4 → `dav-developer`
> （機器可讀副本 `docs/sop/gates.json`）。本檔有詳細 fail-fast 心法。

## 核心原則

在執行工作上，你要跟計劃文檔領取工作任務，也要做好校驗測試，去確保你做出來的結果是完整和完善的；

**核心原則：fail-fast gate** — 不通過 gate = 不可進入 §2.4 反省、不可宣稱任務完成。

完整 Gate 定義（含每個 gate 的 `pass_criteria` / `required_evidence` / `fail_action`）見
[`./sop/gates.json`](./sop/gates.json)。

## 為什麼要 fail-fast gate

> 「寫出來的東西會是錯誤，一行就有問題」 — 這是用戶最常見的痛點。

每一個 gate 都是「比上一個更慢但更深」的校驗。fail-fast 是因為：

- **Gate 2（lint）** 抓「一行就錯」的 syntax / shellcheck 警告 — 修一行 10 秒
- **Gate 4（reviewer）** 抓「自查看不到」的盲點 — 修一個檔案可能要 5 分鐘
- **Gate 漏過 → 累積到 §2.4 反省才發現 → 已經晚了**

關鍵心法：**「先做最便宜的校驗」（Gate 2 只要 1 秒），再做最貴的校驗（Gate 4 reviewer 要 2-5 分鐘）。一旦發現錯誤，越早修越省時間。**

## Gate 3 測試指令的常見陷阱

> v1.3 新增 — 防止「測試跑一半卡住 session」這個最常見的 Gate 3 卡死模式。

Agent shell 在 TTY 偵測上是模糊的。若測試 runner 預設進入 watch / interactive 模式（vitest、jest、某些 `npm test` 設定），shell 會卡住等 stdin，整個
session 凍結（症狀：`Waiting for task (esc to give additional instructions)`）。

**強制規則**：執行 Gate 3 baseline / 修改後測試時，測試指令必須禁用 interactive / watch 模式。

- **vitest**
  - ✅ 正確指令：`vitest run` / `npx vitest --run`
- **jest**
  - ✅ 正確指令：`jest --ci` / `CI=1 npm test -- --watchAll=false`
- **npm test**
  - ✅ 正確指令：加 `CI=1` 前綴，顯式傳 `--watchAll=false`（jest）或 `--run`（vitest）
- **通用保險**
  - ✅ 正確指令：指令後加 `< /dev/null` 強制關 stdin

完整對照表與 fail-fast 自檢條件見 [`dav-developer SKILL.md`](../../../skills/dav-developer/SKILL.md) 的「測試指令執行規範」。

## 失敗處理策略（remediation）

> v1.3 新增（2025-08-24）— 補上「Gate 失敗後怎麼辦」的明確指引，解決 agent 行為不一致的問題。

每一個 Gate 除了 `fail_action`（禁止行為）外，還定義 `remediation`（補救策略）。沒有 `remediation` 時，agent 可能：

- 🟢 自動修（因為 `dav-developer` SKILL 寫「自動修正」）
- 🟡 完全停下來等（因為不確定該不該自動修）
- 🔴 修錯了進入循環（沒有修復上限）

### 三種策略

- **`auto_fix`**
  - 行為：自動修，修好再跑一次 gate（無限次）
  - 適用場景：lint 這種「修一行」的小錯
- **`auto_fix_with_limit`**
  - 行為：自動修，但最多 `max_attempts` 次；用盡後 fallback
  - 適用場景：TDD / regression 這種「可能要改架構」
- **`ask_user`**
  - 行為：立即停下來問用戶
  - 適用場景：reviewer 這種「最終決策要你來」

### 各 Gate 預設

- **Gate 1 (TDD)**
  - strategy：`auto_fix_with_limit`
  - max_attempts：3
  - fallback：ask_user
  - 理由：測試/實作小錯可自調，3 次還不行問你
- **Gate 2 (lint)**
  - strategy：`auto_fix`
  - max_attempts：—
  - fallback：—
  - 理由：幾乎都是一行可修
- **Gate 3 (regression)**
  - strategy：`auto_fix_with_limit`
  - max_attempts：3
  - fallback：ask_user
  - 理由：可能跨多檔，給 3 次機會
- **Gate 4 (reviewer)**
  - strategy：`ask_user`
  - max_attempts：—
  - fallback：—
  - 理由：最終決策本就該是你

> ⚠️ **例外：trust mode 進行中** —— 上表的 `ask_user` 策略與 `ask_user` fallback **不適用**。
> trust 的紀律是「中途不問用戶」（見 dav-trust skill），因此：
> ① Gate 失敗由 Agent 自行決策並寫進 trust-log（可推翻標記）；
> ② 需用戶決定的事寫進 need-you-help 檔，交由用戶在 trust 結束後逐題回覆；
> ③ Agent 不得為了「照 gates.json 策略執行」而中途停下問用戶 —— 那會直接破壞 trust 的執行段。
> （`gates.json` 是預設策略；trust 例外以本節為準，gates.json schema 不變。）

### 本機閘點跑（開發 loop vs push 前）

- **開發中（改完即跑）**：`bash scripts/check-all.sh --changed`
  → 只驗受改動影響嘅探針 ＋ 受影響嘅 mutant 列（≈ 20–40 秒；全量係 ≈ 4 分鐘）
  → 會明講邊步驟跳過同點解跳（base 打錯 → rc=2、冇改動 → rc=1，唔會靜靜哋當通過）
- **push 前（最後一道閘）**：`bash scripts/check-all.sh`（全量 11 步）
- ⚠️ `--changed` **唔等於全量閘通過** → 交付時要講明驗過嘅範圍（`docs/deliverable/` 嘅證據段）

### Agent 必做動作

**進到每一個 Gate 時**，Agent 必須在對話中明確引用該 Gate 的 `mandatory_phrase`
（原文在各承載它的 skill 的「Gate 定義」段，機器可讀副本在 `docs/sop/gates.json`）。
**不引用 ＝ 視為該 Gate 未觸發**（屬「偽裝通過」，見 §2.7 違規回報；TD-016）。

當一個 Gate **失敗**時，Agent 必須：

1. **讀 `gates.json` 的 `remediation.strategy`**
2. **照策略執行**（自動修 / 自動修有上限 / 問用戶）
3. **在對話引用對應的 `mandatory_phrase` + remediation 結果**
   - 例：「依 gates.json 規範，Gate 2 (lint) 需要...已用 `auto_fix` 策略自動修好 3 個錯誤，現在重跑通過 ✅」

### 為什麼這層必要

> 痛點：用戶反映「明明 test 做好了，但 agent 就停下來等」— 根本原因是 SOP 只寫了 fail_action（禁止）沒寫補救，agent 預設保守 = 停下來等。

加了 `remediation` 後：

- ✅ Agent 知道失敗時該「自動修」還是「問用戶」
- ✅ 自動修有上限，避免無限循環
- ✅ 用戶只會在「真正需要決策」時被打擾
- ✅ 整體等待時間預估減少 30-40%

## Gate 4.5 需求對帳（§2.3 尾段子閘，v2.2 新增）

> **為什麼有這道**：執行段的四道大 Gate 驗的是「做得對不對」（測試、lint、回歸、審查），
> 沒有一道驗「做的是不是用戶要的」。交付摘要在傳統流程裡由執行者自己寫 = 自己評自己。
> Gate 4.5 把「用戶原始需求 ↔ 最終成果」的比對交給**未參與實作的獨立 subagent**，
> 讓「成果對不上需求」這類落差在交付前就被看見。

- **位置**：§2.3 執行段結束、**§2.4 反省之前**（先對帳再反省：對帳是事實比對，反省是觀點評析；
  順序反了會讓反省建立在未經驗證的「已完成」前提上）
- **觸發 skill**：`/skill:dav-reconciler`（需同套安裝）
- **輸入**：專案端需求錨點檔（`docs/req/<US-ID>-requirement.md`）+ 本次最終變更清單
- **輸出**：專案端 `docs/reconcile/<US-ID>-reconcile.md`（需求對帳表）+ 交付摘要的「需求對帳」段
- **通過條件**：
  1. 對帳表覆蓋錨點的**全部 R-ID**（覆蓋率 100%；漏列視同未對帳）
  2. 對帳由**未參與實作**的 subagent 執行（環境無 subagent 能力時可降級，但必須標註
     「⚠️ 對帳降級（無獨立 subagent）」，且不得宣告對帳通過）
  3. 對帳結果已帶入交付摘要，且交付狀態與對帳結果一致
- **不通過 = 不可進入 §2.4 反省**：
  - 任一 R-ID 為「部分實作／未實作」→ 交付狀態**不得**標「✅ 完成」，只能「⚠️ 部分完成」+ 待補清單
  - 對帳缺失 / R-ID 未覆蓋 / 降級未標註 → 同樣不得標「✅ 完成」
- **mandatory_phrase**：「依 §2.3 規範，Gate 4.5 (需求對帳) 需要：對帳表覆蓋全部 R-ID + 獨立 subagent 對帳原文 + 交付狀態與對帳結果一致，並在對話貼出對帳表與覆蓋率。」
- **定位說明**：Gate 4.5 是 **§2.3 內嵌的子閘**，**不進 `gates.json`**（該檔的 gate `id` 受 schema 限制，
  只允許整數編號的四大 Gate；見 `docs/prd/05-delivery-fidelity.md` ADR-D1）。自 2026-10-26 起，
  四道大 Gate 的**定義本體**落在各自承載它的 skill（gate-1/2 → `dav-developer`、gate-3 →
  `dav-developer`、gate-4 → `dav-developer`），`gates.json` 為**機器可讀副本**；
  （2026-10-27 減法：鎖兩邊逐條一致嘅 `tests/gate-in-skill.bats` 已刪 → 兩邊要人手同步。）
- **例外**：存量任務（無需求錨點）不觸發；trust mode 進行中不中途停下問用戶，
  對帳結果照常產出、缺口記入 trust-log 代答 + need-you-help 檔待回覆。

## 必要守護（bats 探針判斷準則，v2.0 新）

> 來源：TMO-008 / PRD-03（v2.0）。定義哪些情境**必加**探針、哪些情境**不加**。避免「為證明工作而加」的探針。

### 加探針的條件（符合任 1 個）

- **SOP 章節被修改（防止靜默移除）**
  - 範例：v1.8 加 §4.6 模板存在探針
- **跨檔一致性（文件 A 提到 B、B 確實存在）**
  - 範例：backlog.md 提到的 AC 檔案真的存在；SKILL.md 引用的 playbook 真的存在
- **已知 bug 修復（防止復發）**
  - 範例：wiki-extract-media env 缺失 → 加探針警告
- **跨章節語意（同名章節衝突避免）**
  - 範例：v1.9 §2.7 跨檔語意衝突 → 加探針驗證連結

### 不加探針的情境

- **「為證明工作」而加**
  - 理由：沒有實際守護價值，只為「看起來有測試」
- **「feature creep 守護」**
  - 理由：測試本來就要測的功能（已有 Gate 1/2/3 覆蓋）
- **「為了 sprint 結束 KPI」**
  - 理由：數字不是目的，守護才是
- **「過細 substring grep 易誤判」**
  - 理由：改用 awk 範圍限縮或精確 row 格式比對
- **唔係規則本體嘅**純 markdown 文字層改動（行為不變、行數自查已覆蓋）
  - 理由：V03 文件分支只需自查行數上限；SOP 章節（handbook）本身仍按上面「加探針的條件」第 1 條處理；
    改規則語意而要加探針者 → 屬規範語意，按 V03 例外走二審

### 怎麼判斷（決策流程）

```
考慮加探針 →

  1. 這個變更 1 年後有人可能偷偷拿掉嗎？ ──是→ 加
  2. 這個變更跨越多個檔案有相互引用嗎？ ──是→ 加
  3. 之前修過同類 bug 嗎？ ──是→ 加
  全部否 → 不加，記得在 PR/commit message 說明為什麼不加
```

### 「先紅後綠」紀律（v2.0 加強）

- 加探針前**必先跑一次確認紅**
- 實作完成後再跑一次確認綠
- 對話必貼「紅 + 綠」兩次輸出作為 Gate 1 證據
