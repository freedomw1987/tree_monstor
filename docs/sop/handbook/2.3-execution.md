# §2.3 執行（開發編程任務）

> 本檔是 AGENTS.md §2.3 的詳細內容。引用：`[§2.3](./sop/handbook/2.3-execution.md)`
>
> AGENTS.md 內保留 4 Gate 表格 + 必要動作指示；本檔有詳細 fail-fast 心法。

## 核心原則

在執行工作上，你要跟計劃文檔領取工作任務，也要做好校驗測試，去確保你做出來的結果是完整和完善的；

**核心原則：fail-fast gate** — 不通過 gate = 不可進入 §2.4 反省、不可宣稱任務完成。

完整 Gate 定義（含每個 gate 的 `pass_criteria` / `required_evidence` / `fail_action`）見
[`./sop/gates.json`](./sop/gates.json)。

## 為什麼要 fail-fast gate

> 「寫出來的東西會是錯誤，一行就有問題」 — 這是用戶最常見的痛點。

每一個 gate 都是「比上一個更慢但更深」的校驗。fail-fast 是因為：

- **Gate 2（lint）** 抓「一行就錯」的 syntax / shellcheck 警告 — 修一行 10 秒
- **Gate 4（reviewer）** 抓「自查看不到」的盲點 — 修一個檔案可能要 5 分鐘
- **Gate 漏過 → 累積到 §2.4 反省才發現 → 已經晚了**

關鍵心法：**「先做最便宜的校驗」（Gate 2 只要 1 秒），再做最貴的校驗（Gate 4 reviewer 要 2-5 分鐘）。一旦發現錯誤，越早修越省時間。**

## Gate 3 測試指令的常見陷阱

> v1.3 新增 — 防止「測試跑一半卡住 session」這個最常見的 Gate 3 卡死模式。

Agent shell 在 TTY 偵測上是模糊的。若測試 runner 預設進入 watch / interactive 模式（vitest、jest、某些 `npm test` 設定），shell 會卡住等 stdin，整個 session 凍結（症狀：`Waiting for task (esc to give additional instructions)`）。

**強制規則**：執行 Gate 3 baseline / 修改後測試時，測試指令必須禁用 interactive / watch 模式。

| Runner | ✅ 正確指令 |
|---|---|
| vitest | `vitest run` / `npx vitest --run` |
| jest | `jest --ci` / `CI=1 npm test -- --watchAll=false` |
| npm test | 加 `CI=1` 前綴，顯式傳 `--watchAll=false`（jest）或 `--run`（vitest）|
| 通用保險 | 指令後加 `< /dev/null` 強制關 stdin |

完整對照表與 fail-fast 自檢條件見 [`regression-guard SKILL.md`](../../skills/regression-guard/SKILL.md) 的「測試指令執行規範」。

## 失敗處理策略（remediation）

> v1.3 新增（2025-08-24）— 補上「Gate 失敗後怎麼辦」的明確指引，解決 agent 行為不一致的問題。

每一個 Gate 除了 `fail_action`（禁止行為）外，還定義 `remediation`（補救策略）。沒有 `remediation` 時，agent 可能：

- 🟢 自動修（因為 `regression-guard` SKILL 寫「自動修正」）
- 🟡 完全停下來等（因為不確定該不該自動修）
- 🔴 修錯了進入循環（沒有修復上限）

### 三種策略

| 策略 | 行為 | 適用場景 |
|------|------|----------|
| `auto_fix` | 自動修，修好再跑一次 gate（無限次） | lint 這種「修一行」的小錯 |
| `auto_fix_with_limit` | 自動修，但最多 `max_attempts` 次；用盡後 fallback | TDD / regression 這種「可能要改架構」 |
| `ask_user` | 立即停下來問用戶 | reviewer 這種「最終決策要你來」 |

### 各 Gate 預設

| Gate | strategy | max_attempts | fallback | 理由 |
|------|----------|--------------|----------|------|
| Gate 1 (TDD) | `auto_fix_with_limit` | 3 | ask_user | 測試/實作小錯可自調，3 次還不行問你 |
| Gate 2 (lint) | `auto_fix` | — | — | 幾乎都是一行可修 |
| Gate 3 (regression) | `auto_fix_with_limit` | 3 | ask_user | 可能跨多檔，給 3 次機會 |
| Gate 4 (reviewer) | `ask_user` | — | — | 最終決策本就該是你 |

### Agent 必做動作

當一個 Gate 失敗時，Agent 必須：

1. **讀 `gates.json` 的 `remediation.strategy`**
2. **照策略執行**（自動修 / 自動修有上限 / 問用戶）
3. **在對話引用對應的 `mandatory_phrase` + remediation 結果**
   - 例：「依 gates.json 規範，Gate 2 (lint) 需要...已用 `auto_fix` 策略自動修好 3 個錯誤，現在重跑通過 ✅」

### 為什麼這層必要

> 痛點：用戶反映「明明 test 做好了，但 agent 就停下來等」— 根本原因是 SOP 只寫了 fail_action（禁止）沒寫補救，agent 預設保守 = 停下來等。

加了 `remediation` 後：

- ✅ Agent 知道失敗時該「自動修」還是「問用戶」
- ✅ 自動修有上限，避免無限循環
- ✅ 用戶只會在「真正需要決策」時被打擾
- ✅ 整體等待時間預估減少 30-40%
