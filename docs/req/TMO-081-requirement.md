### 觸發點

做 TMO-079 時重新量測咗 PNA-4 嘅立論前提，發現**原文寫錯**：

| 原文寫（commit `9c04aaa`） | 實測（bats 1.14.0 ＝ CI pin 嘅版本） |
| --- | --- |
| 「獨立的 `[[ ... ]]` 斷言失敗**不會中止 test body**」 | **會中止** |
| 「bash 3.2 唔中止、bash 5.x 會中止」 | **兩個版本一樣中止** |

證據：`bats 1.14.0` 同 `1.11.1` 嘅 `libexec/bats-core/bats-exec-test` 開頭都係 `set -eET`，而 test body 喺
`{ setup "$@"; "$@"; }` 呢個**唔受 `-e` 忽略**嘅語境入面跑 → 獨立嘅 `[[ ]]` 失敗**會**中止 test body。
實測（`bats --print-output-on-failure`）：T1~T7 全部 `not ok`，`echo reached` 一次都冇印出。

**後果**：PNA-4 唔再係「唯一防止靜默失敗」嘅東西 → 佢而家只剩「風格／診斷品質」嘅價值。
該更正已於 TMO-079 內完成（前提改寫 ＋ 重新定位 ＋ `changelog.md` v2.15 ＋ 歷史交付摘要加 pointer）。
**本票只處理「既然咁，PNA-4 應唔應該繼續存在」呢個問題。**

### 由數據推出嘅三個關鍵事實

1. **PNA-4 唔係「零價值」**：repo **已經在用** `set +e`（3 處）。喺嗰種窗口裡面，裸 `[[ ]]` 嘅失敗
   **真係會被靜默吞掉**（`set +e` 令該窗口內嘅 errexit 失效）→ 呢個係**真·會假綠**嘅場景，
   而唔係假設性嘅未來風險。
2. **但規則嘅「理據」錯咗**：PNA-4 而家守住嘅係「所有裸斷言都要包 fail-fast」呢個**風格**要求，
   而唔係「防止靜默失敗」——因為除咗 `set +e` 窗口，bats 自己已經會中止並印出 `file:line`。
3. **「刪規則」同「還原 181 條改寫」係兩件唔同嘅事**：236 條 fail-fast 改寫**唔會**造成任何損害，
   而且佢哋係診斷訊息嘅來源（`FAIL: <file>:<line>`）。真正嘅「減法」目標如果係診斷品質，
   應該係**收窄規則**，而唔係還原改寫。

### 可行性檢查（2026-10-26，評估階段新增；推翻咗初稿嘅建議）

| 檢查項 | 實測結果 | 對方案嘅影響 |
| --- | --- | --- |
| `set +e` 喺 bash 裡嘅作用域 | **shell 全域**（唔係 function-local）→ function 內 `set +e` 會把**呼叫者**之後嘅 errexit 一齊關掉（實測：function 內 `set +e` → 呼叫者隨後嘅 `false` 都唔會中止） | ⚠️ **方案 C 靜態不可靠**（見下） |
| corpus 內 3 個 `set +e` 窗口嘅內容 | 每個 4 行（`set +e` → 跑命令 → `local rc=$?` → `set -e`），窗口內裸 `[[ ]]` = **0 條** | C 要守嘅場景**目前唔存在於 corpus**（純前瞻） |
| PNA-4 現行對嗰 3 個窗口嘅輸出 | violations = **0** | 現行規則已覆蓋（且係 C 嘅**超集**） |

### 方案 C 嘅致命問題（可行性檢查發現）

C 嘅核心係「只守 `set +e` 窗口內嘅裸斷言」，但：

1. **窗口嘅結束點唔可靜態判定** —— bash 嘅 `set +e` 係 **shell 全域**開關（實測見上）。
   所以一個寫喺 helper function 裡面嘅 `set +e`，會令**整個 test body 餘下部分**都失去 errexit，
   而「邊一行恢復」喺靜態掃描入面**無法確定**（可能喺另一個 function、可能根本冇恢復）。
   → 靜態掃描要嘛**漏報**（窗口實際延伸到測試結尾，但掃描器以為到 `set -e` 就完 → **假綠方向**），
   要嘛過度保守。**違反 repo 核心原則「守門失效＝假綠」。**
2. **C 唔係簡化** —— C 仍然需要同一套 ②（偵測獨立斷言）＋ ④⑤⑥（排除 guard／`return 1`／`|| {`）
   ＋ ⑦（test body 最後一句）邏輯，**再加** `set +e` 作用域追蹤 → 成本**高於**現行方案。
3. **C 嘅保護係 A 嘅真子集** —— A（現行）報所有裸斷言，自然包含 `set +e` 窗口內嘅；
   C 只報窗口內嘅 → **A ⊃ C**。

⇒ **C 被 A 完全支配**（保護更廣、成本更低、無可靠性風險）→ **唔建議 C**。

### 「如果唔做」（保留現狀）嘅風險

| 面向 | 評估 |
| --- | --- |
| 假綠風險 | **低**。現行 violations = 0、corpus 新舊零差異；規則只會**多報**唔會少報 → 唔會製造假綠 |
| 保護價值 | **唔係零**。A ⊃ C → 規則同時守住 `set +e` 窗口（repo **已在用**嘅真·假綠面）同裸斷言嘅診斷品質 |
| 持續成本 | 掃描器 177 行 ＋ 3 支 canary ＋ 3 支 mutant ＋ 732ms/666 支 → **A 唯一嘅實質代價** |
| 理據 | 前提已於 TMO-079 更正 → 規則已**唔再**聲稱自己防止靜默失敗；定位寫實為「風格／可讀性守門」 |
| 刪除嘅風險 | 失去機械守門 → 裸斷言可回潮 → 若日後有人喺 `set +e` 窗口寫裸斷言 → **真·假綠** |

⇒ 刪除嘅風險（失去對 `set +e` 窗口嘅保護）**大於**保留嘅成本 → **保留現狀**。

### 評估結論（決策）

**採用方案 A（保留現狀，唔改任何嘢）。**

1. **A ⊃ C** —— 現行規則已經守住 `set +e` 窗口（唯一真·會假綠嘅場景）；C 只會**收窄**保護，唔會增加。
2. **C 技術上唔可靠** —— `set +e` 係 shell 全域開關 → 靜態掃描無法確定窗口結束點 → 要嘛漏報
   （假綠方向）→ 違反 repo 核心原則。
3. **A 成本最低** —— 前提更正已完成（TMO-079），本票唔需任何實作改動；持續成本
   （177 行掃描器 ＋ 6 支探針/mutant）換走咗「唔會回潮」同「對真·假綠面嘅保護」。

**B／D 明確唔建議**：兩者都會失去對 `set +e` 窗口嘅保護；D 額外拎走 `FAIL: <file>:<line>` 診斷訊息。
**C 唔建議**：被 A 支配 ＋ 靜態不可靠。

**本票唔產生實作改動**（符合「只做評估同決策」）。若日後仍想減 fail-fast 嘅寫作負擔，
正確做法係**先**提供一個可靠嘅 `set +e` 作用域機制（例如改 runtime 探測 ＋ 探針自證），
**之後**另開票 —— 唔可以靜態掃描硬做。
