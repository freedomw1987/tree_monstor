# TMO-082 需求錨點

> US: TMO-082 | 建立: 2026-10-26 | 來源: 用戶對話（框架「繼續優化和減磅」）

## 用戶原話（唯讀）

- R1: 「可以幫我為這個框架繼續優化和減磅」
- R2: 「A+D」（回覆我提出嘅四個範圍選項：**A** = Context 瘦身刀、**B** = 治理文件刀、**C** = 衍生膨脹上限、**D** = 瘦身可視化 + 防回潮；A+D 為最推薦）

## 背景（非用戶原話；係 TMO-075 第一刀收尾時量測到嘅實測數據）

TMO-075（第一刀）砍咗框架嘅 meta 自我管理層，但佢自己嘅 §6.2／§6.3 留低咗未做嘅方向：

- §6.2「第二刀：砍『框架治理』類文件（`docs/system-design.md`、`docs/DESIGN.md`、AGENTS.md 的重複說明）——需先確認 live dependency」
- §6.3「讓框架自我管理層的膨脹率可見：每個 sprint 產出『框架行數 / 產品行數』的趨勢圖，比例上升就是紅燈」
- §6.1-3「把『每個 US 產生 N 份產物』的比例寫成一條探針」

**動工前嘅實測（2026-10-26，`git ls-files` + `wc -l`）**：

| 量度對象 | 數值 | 口徑 |
| --- | --- | --- |
| repo tracked 總行數 | 48,048 | `git ls-files` + `wc -l` |
| skills/（產品層） | 21,350 | 同上 |
| tests/（守護層） | 16,265 | 同上 |
| docs/（治理層） | 6,706 | 同上 |
| **agent 觸發 skill 嘅讀入量**（SKILL.md + 支援 .md） | **9,619** | 13 個 skill 合計（**唔含** CHANGELOG；口徑：`scripts/ci/check-framework-weight.py` 嘅 `total_context_lines`）|
| 最重三個 skill | regression-guard 2,495、dav-wiki 1,354、dav-trust 1,186 | 同上（同一把尺量）|

**關鍵判斷**：總行數唔係最痛嘅位——**高頻成本**先係。治理文件（`system-design.md` 等）係一次性、低頻讀取；
而 skill 嘅支援檔係**每次觸發 skill 都要讀落 context**。故第二刀先切支援檔（A），再裝尺（D）。

## 澄清後驗收句

- R1: 必須**先量測現況**再減磅；減磅目標係 **agent 每次觸發 skill 嘅 context 成本**
  （唔係 repo 總行數）；**不得犧牲任何被探針錨定嘅內容契約**（含探針錨點嘅字串、段落結構、檔案存在性）。
- R2: 必須同時交付「瘦身」同「防回潮」：減磅後要有**可量度嘅守門**並接入 CI；
  守門必須**自己都有探針證明會紅**（壞情境：超預算／死指標／子檔被掏空／枚舉壞咗／ratio 超標），
  且**唔准假綠**（不得 `|| true` / `continue-on-error`）。

## 執行約束（repo 既有規則，唔屬驗收句）

- 本票改 `skills/`（skill 子檔）同 `tests/`（新探針）→ 依 `AGENTS.md` §1.5 **V03 必須走獨立 Reviewer 二審**
  （附風險分級 ＋ 跨 SOP 一致性檢查）。
- 新探針嘅 `@test` 名**必須全 ASCII**（`tests/probe-name-ascii.bats` PNA-1：bash 3.2 ＋ UTF-8 locale
  下中文名會被 bats **靜默丟棄** → 本機假綠）。
- 新增／修改 markdown 必須過 markdownlint（MD013 = 120）；探針檔名／訊息亦受 PNA-4（fail-fast 慣例）規管。
