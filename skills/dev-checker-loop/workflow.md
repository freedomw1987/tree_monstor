# Dev-Checker Loop 工作流程

## Dev Agent 工作流程

### 步驟 1：領取任務

| 步驟 | 操作 | 目的 |
|------|------|------|
| 1.1 | 讀取 `docs/backlog.md` | 查看待處理任務 |
| 1.2 | 篩選狀態為"PENDING"的任務 | 找到可領取的任務 |
| 1.3 | 選擇一個任務（按優先級或順序） | 決定本次處理目標 |
| 1.4 | 更新任務狀態為"進行中" | 避免重複領取 |

**目的：** 確保每個任務只被一個 dev 處理，避免衝突。

### 步驟 2：開發任務

| 步驟  | 操作                                                                 | 目的          |
| --- | ------------------------------------------------------------------ | ----------- |
| 2.1 | 讀取對應 Module 的 PRD 文檔                                               | 了解功能需求和驗收標準 |
| 2.2 | 按 PRD 進行開發                                                         | 實現功能需求      |
| 2.3 | 參照 [[skills/regression-guard/SKILL\|skills:regression-guard]] 埋入探針 | 預留測試點       |
| 2.4 | 進行自我測試驗證                                                           | 確保功能正常      |

**目的：** 按照規格開發，並預留測試覆蓋。

### 步驟 3：標記完成

| 步驟 | 操作 | 目的 |
|------|------|------|
| 3.1 | 更新任務狀態為"等待校驗" | 通知 checker 進行校驗 |
| 3.2 | 如有發現問題，則改為"需修復" | 主動發現問題需修復 |

**目的：** 將任務交給 checker 進行品質把關。

### 步驟 4：處理修復任務（循環）

| 步驟 | 操作 | 目的 |
|------|------|------|
| 4.1 | 持續監控 backlog | 發現"需修復"狀態的任務 |
| 4.2 | 領取修復任務 | 處理 checker 發現的問題 |
| 4.3 | 修復問題並更新狀態為"等待校驗" | 完成修復並重新校驗 |
| 4.4 | 重複直到問題修復或循環達上限 | 持續修復直到通過 |

**目的：** 持續修復直到 checker 確認通過。

## Checker Agent 工作流程

### 步驟 1：監控 Backlog

| 步驟 | 操作 | 目的 |
|------|------|------|
| 1.1 | 持續讀取 `docs/backlog.md` | 監控狀態變化 |
| 1.2 | 篩選狀態為"等待校驗"的任務 | 找到待校驗任務 |
| 1.3 | 如有新任務則開始校驗 | 及時處理 |

**目的：** 及時發現需要校驗的任務。

### 步驟 2：全面校驗

| 檢查範圍 | 檢查內容 | 目的 |
|---------|---------|------|
| **功能正確性** | 對照 PRD 驗證功能是否符合規格 | 確保功能正確 |
| **代碼品質** | 檢查代碼風格、安全性、可讀性 | 確保代碼品質 |
| **測試覆蓋** | 檢查是否有對應的測試 | 確保測試完整 |
| **Regression 探針** | 驗證探針是否正確運行 | 確保有自我測試機制 |

### 步驟 3：記錄問題

| 步驟 | 操作 | 目的 |
|------|------|------|
| 3.1 | 發現問題則在 backlog 中新增 Defect 條目 | 記錄問題 |
| 3.2 | 將原任務狀態改為"需修復" | 通知 dev 修復 |
| 3.3 | 如有循環次數記錄需遞增 | 追蹤修復次數 |

**目的：** 清晰記錄問題，讓 dev 知道需要修復什麼。

### 步驟 4：通過驗收

| 步驟 | 操作 | 目的 |
|------|------|------|
| 4.1 | 所有檢查通過 | 確認任務品質 |
| 4.2 | 更新任務狀態為"已完成" | 標記任務完成 |
| 4.3 | 記錄完成時間 | 追蹤進度 |

**目的：** 確認任務符合品質標準。

## 循環控制

### 循環計數機制

每個問題（Defect）都有循環計數器：

| 計數器值 | 意義 |
|---------|------|
| 0 | 問題剛被記錄 |
| 1-19 | 正常修復循環中 |
| 20 | 達到上限 |

### 循環中斷處理

當循環計數達到 20：

| 處理方式 | 說明 |
|---------|------|
| 記錄警告 | 在 backlog 中標記"達到循環上限" |
| 通知用戶 | 告知用戶需要人工介入 |
| 停止自動修復 | 該問題不再自動處理 |

## Backlog 狀態機

```
PENDING ──▶ 進行中 ──▶ 等待校驗
                │            │
                │            ▼
                │         需修復 ──▶（循環）──▶ 等待校驗
                │            │
                ▼            ▼
             已完成 ◀───────┘
                │
                ▼
            已放棄（循環達上限）
```

## 協作默契

| 原則 | 說明 |
|------|------|
| **Dev 不干擾 Dev** | 同一時間只有一個 dev 處理同一任務 |
| **Checker 客觀公正** | 嚴格按照標準檢查，不妥協 |
| **循環有上限** | 避免無限修復，20 次上限保護 |
| **記錄清晰** | 每個問題都有明確的描述和追蹤 |
