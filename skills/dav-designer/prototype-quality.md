# Prototype Quality Sub-spec

> 本檔為 `dav-designer` skill 的子檔，補充說明互動原型的品質規範。SKILL.md 為入口，本檔為細節。

## 0. DoD 深度模式（v2.2 新增）

互動原型有兩種 DoD 深度，在 Step 1 一次選定：

| 模式 | 必做狀態 | 略過狀態 | 預設？ |
|------|----------|----------|--------|
| **DoD-Lite** | Happy path（§1.1）| Loading / Empty / Error / Edge | ⭐ 預設 |
| **DoD-Full** | Happy + Loading + Empty + Error + Edge（§1.1-§1.5）| （無）| 選用 |

詳細選擇時機見 SKILL.md Step 1。

## 1. 原型 DoD（Definition of Done）

互動原型完成前必含狀態，每種都有最低實作要求。**實際要做哪些依 Step 1 選定的 DoD 深度**。

### 1.1 Happy path（主流程）— **必做**

| 必含 | 說明 |
|------|------|
| 主流程完整 | 從入口到出口的所有步驟都能點擊走完 |
| 表單驗證 | 必填欄位未填時擋下、提示訊息 |
| 成功回饋 | 完成後有明確成功狀態（toast / 跳頁 / 訊息）|

### 1.2 Loading 狀態

| 必含 | 說明 |
|------|------|
| 至少 1 個 spinner / skeleton | 送資料中顯示 |
| 按鈕 disable | loading 期間 CTA 不可重複點擊 |
| 最短顯示時間 ≥ 300ms | 避免 loading 閃一下就消失（體驗差）|

### 1.3 Empty state（空狀態）

| 必含 | 說明 |
|------|------|
| 至少 1 個零資料畫面 | 如「沒有待辦」「沒有訂單」 |
| 明確圖示 + 文字 | 不可只放空白 |
| 引導動作 | 提示「建立第一個 X」CTA |

### 1.4 Error state（錯誤狀態）

| 必含 | 說明 |
|------|------|
| 表單錯誤 | 密碼錯誤、Email 格式錯等 |
| 系統錯誤 | 「網路斷線」「伺服器錯誤」 |
| 錯誤訊息具體 | 不可只寫「發生錯誤」，要告訴用戶如何修正 |

### 1.5 Edge case（邊界輸入）

| 必含 | 說明 |
|------|------|
| 超長字串 | 輸入框貼 1000 字元是否正常顯示 / 截斷 |
| 特殊字元 | Emoji、`<script>`、SQL 注入字串 |
| 邊界數值 | 數量 = 0、= 999999、= -1 |

## 2. 設計自審 5 維度（Step 4.5）

Agent 跑完 PRD/DESIGN/system-design 後、進 Step 5 之前，依下列 5 維度逐項檢查並產出「自審報告」。

### 2.1 一致性（Consistency）

| 檢查項 | 範例 |
|--------|------|
| 相同操作跨 Module 統一 | 「刪除確認」按鈕位置 / 顏色一致 |
| 相同元件命名統一 | 不可 Module A 叫「用戶」、Module B 叫「會員」|
| 錯誤訊息格式統一 | 全部用 toast 或全部用 inline，不可混用 |

**不通過時**：統一風格後重生 Step 4。

### 2.2 可達性（Reachability）

| 檢查項 | 範例 |
|--------|------|
| 所有功能都能從主流程點到 | 無孤島畫面（存在但無入口）|
| 深層路徑 ≤ 3 層 | 超過 3 層需重新設計導航 |
| 必經節點有 breadcrumb 或返回鍵 | 用戶不會迷路 |

**不通過時**：加導航或刪除孤島畫面。

### 2.3 錯誤處理（Error handling）

| 檢查項 | 範例 |
|--------|------|
| 每個表單有對應錯誤狀態 | 登入失敗、註冊重複 Email |
| API 失敗有 fallback | 「無法載入，請重試」|
| 邊界輸入不當機 | 超長字串、特殊字元不破版 |

**不通過時**：補錯誤狀態（納入 Step 5 DoD）。

### 2.4 空狀態（Empty state）

| 檢查項 | 範例 |
|--------|------|
| 零資料畫面有設計 | 「尚未建立任何 X」|
| 零搜尋結果畫面有設計 | 「找不到符合條件的項目」|
| 首登體驗（Onboarding）| 新用戶看到的第一個畫面不是空白 |

**不通過時**：補空狀態畫面（納入 Step 5 DoD）。

### 2.5 效能預感（Performance anticipation）

| 檢查項 | 範例 |
|--------|------|
| 大量資料 loading | 列表 1000 筆時是否有分頁 / 虛擬捲動 |
| 重操作 loading | 上傳檔案、批次處理是否有進度條 |
| 即時操作節流（throttle）| 搜尋框輸入是否有 debounce |

**不通過時**：補 loading 狀態（納入 Step 5 DoD）或回 Step 3 調整架構。

## 3. 自審報告模板（Agent 產出格式）

```markdown
## 設計自審報告 — Module X

| 維度 | 結果 | 備註 |
|------|------|------|
| 一致性 | ✅ 綠 / ⚠️ 待修 / ❌ 不通過 | ... |
| 可達性 | ✅ 綠 / ⚠️ 待修 / ❌ 不通過 | ... |
| 錯誤處理 | ✅ 綠 / ⚠️ 待修 / ❌ 不通過 | ... |
| 空狀態 | ✅ 綠 / ⚠️ 待修 / ❌ 不通過 | ... |
| 效能預感 | ✅ 綠 / ⚠️ 待修 / ❌ 不通過 | ... |

**結論**：全綠 → 進 Step 5 / 有 ⚠️❌ → 用戶決定「退回修改」或「帶條件進 Step 5」

請用戶簽核：「✅ 簽核」或「🔙 退回修改：...」
```
