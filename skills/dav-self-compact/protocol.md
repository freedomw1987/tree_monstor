# dav-self-compact — 通用程序（跨 host）

> 主檔只講「做乜」；呢度講「點做」。各 host 嘅量度／觸發差異 → 同套 `./adapters.md`。

## §1 區間定義（聰明區）

- **smart（聰明區）**：`percent < softPercent`（默認 50%）→ 照常做，唔使理 context。
- **soft block**：`percent >= softPercent`（50%）→ 軟阻塞：開始為壓縮做準備（寫交接筆記、記低下一步），**唔代表要即刻壓**。
- **opportunity（機會窗口）**：`percent >= opportunityPercent`（55%）→ **最佳壓縮時機**：揀一個好邊界就壓，唔好再等。
- **hard block**：`percent >= hardPercent`（60%）→ **死線／警報**：正常應該已壓過；仍見到代表保險絲太遲，要收尾 ＋ 報告。
- **target（壓縮後落點）**：建議 20%–35%；硬規定只有一條 —— 壓縮後必須 ≤ softPercent（50%）。
- `percent` = 已用 tokens ÷ 有效窗口；設咗絕對上限時，有效窗口 = min(真實窗口, 絕對上限)。
- 對應 action：smart→keep_working／soft→prepare_then_compact／opportunity→compact_at_boundary／hard→compact_now。
- **點解要有絕對上限**：1M 窗口嘅 50% = 500k tokens，比例睇落「安全」，但注意力喺咁上下文明顯退化 → 絕對上限先真正貼近「聰明區」。

## §2 量度（通用）

- **量度來源優先序**：host 專用工具 → transcript 檔解析 → UI 顯示（人要代報）→ 粗略估算（對話字數 ÷ 4 ÷ 窗口）。
- **查詢時機**：進入新階段、連續 20＋ 次工具呼叫、覺得「唔記得早前做咗乜」、見到里程碑提示。
- **唔好每個工具呼叫都量**（量度本身都燒 token）。
- **UI 顯示嘅 % 唔可以直接用**：分母係真實窗口；設咗絕對上限時 UI 顯示 30% 其實已過 hard → 要用 tokens 換算。
- **攞唔到 usage** → 當 soft 區保守處理：寫交接筆記、避開大讀取、唔開新大範圍工作，唔好亂報數。
- **壓縮剛做完** → usage 會變 null／unknown（要等新一次模型回應）→ 唔係錯誤，等下一輪再量。

## §3 執行程序

### soft（≥50%）：準備

1. 判斷仲有幾多工作：剩低好多輪 → 值得準備；剩低一兩步 → 可以繼續做，唔使急。
2. 寫交接筆記（§4），落檔案。
3. 避開大讀取：只讀必要段落（offset／limit）或者叫 subagent 讀完只交結論。
4. 把剩低工作切成細步，令每一步都可以喺 hard 之前收尾。
5. 唔使自己叫壓縮；但**筆記要由呢一刻起保持最新**（之後任何一個回合邊界都可能壓縮）。

### opportunity（≥55%）：揀最好時機

- 好邊界四條件（全部成立先叫好時機）：原子步驟已完成（檔已寫、測試已跑）／測試綠或已記錄紅在哪／交接筆記已更新／冇不可中斷嘅背景動作（部署、長 bash、大範圍 rename）。
- 反例：改檔改到一半、測試跑緊、下一步係未拆步嘅大範圍重構。
- 窗口內做乜：唔准開新嘅大範圍工作；主動造出好邊界（收尾當前步 → 更新筆記 → 呢一輪就係邊界）；用 adapter 嘅觸發方式壓縮 → 壓完繼續做，唔好停低等人。
- 唔准為咗「等更好嘅時機」拖過 hard —— 保險絲睇 token 數，唔識分辨好壞時機；拖得越久越可能被迫喺 hard 之後甚至 overflow 之後壓（摘要會夾雜失敗嘗試）。
- 壓縮工具報「冇嘢可壓」→ 對話未過該 host 嘅保留門檻 → **唔准硬 loop 重叫**，照樣繼續做落去。

### hard（≥60%）：死線

1. 唔准開新工作：只把手上步驟收尾（不可中斷嘅寫檔／部署就等佢完成）。
2. 收尾即更新交接筆記（§4）。
3. 停手交俾原生壓縮：host 引擎喺回合邊界自動壓縮、壓完繼續跑 —— 你只需要「唔再開新工作」。
4. 見到 hard 係警報：正常情況保險絲應該喺 opportunity（55%）已開火 → 仍然見到代表保險絲太遲（常見原因：一次過嘅工具輸出太肥，個步驟跨咗門檻）→ 報告 ＋ 建議改閾值。
5. 壓縮失敗／太細（session too small）＝正常（未過保留門檻）；其他錯誤 → 報告，唔好硬 loop 重試。

## §4 交接筆記模板（最少三項）

```markdown
# 任務交接筆記 — <任務名> — <YYYY-MM-DD HH:MM>

## 已完成
- [x] <做咗咩／邊個檔案>

## 而家卡喺邊
- <下一步要即刻做嘅嘢，一句講清>

## 下一步（按次序）
1. <步驟 1>
2. <步驟 2>

## 關鍵檔案路徑
- `path/to/file.ts` — <點用>

## 關鍵決定同約束
- <做過嘅取捨、唔可以違反嘅嘢>

## 未解決問題
- <仍然未答、或者要問用戶嘅嘢>
```

- **必須落檔案**：摘要會壓縮細節，檔案先係真相；壓縮後第一件事係讀返呢份筆記。建議位置 `docs/ctx-handoff/<task-slug>.md`；冇 `docs/` 就放工作目錄根。
- **覆寫而唔係追加**：保持「最新狀態」，唔好變日誌。
- **寫得夠密**：摘要會保留嘅係「有寫落筆記嘅嘢」，冇寫嘅等於自願失憶。

## §5 壓縮後驗證

- 壓縮後 usage 變 null／unknown → **唔准即刻報「已回落」**。
- 下一輪回應之後即刻再量：合格線 ≤50%，目標 20%–35%。
- 唔合格 → 通常係交接筆記太薄或對話有超大字串（貼咗長 log）→ 補筆記 → 再壓。
- 想確認真係壓縮咗（唔止 usage 跌）：睇 transcript 有冇 compaction 標記
  （pi：session JSONL `"type":"compaction"`；Claude Code：`compact_boundary`；Qoder：壓縮事件）。
- 連續兩次壓縮都唔跌返 ≤50% → 停低報告：邊個步驟令 context 爆（通常係讀大檔／貼長 log），建議拆細。

## §6 長任務紀律

- 每個階段結束就寫交接筆記，唔好等到真係要壓縮先寫（到時可能記唔起）。
- 唔好靠對話長期記住狀態：跨階段事實（做咗乜、改咗邊個檔、仲有咩未做）一律落檔案。
- 大輸出唔好入 context：長 log／大檔案 → 摘要落檔案，context 只留摘要同路徑。
- subagent 結果：只攞結論同路徑返嚟，唔好將完整推理帶返嚟（context 貴）。
- 壓縮後開工第一步：讀交接筆記，唔好靠摘要嘅記憶亂猜。
