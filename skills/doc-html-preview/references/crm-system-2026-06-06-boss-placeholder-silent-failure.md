# crm-system Day 9 — boss HTML silent-placeholder failure

**Date**: 2026-06-06
**Project**: `~/www/crm-system`
**Skill**: `doc-html-preview` (loaded during this session, but the lesson was about what the skill WASN'T enforcing)

## What happened

I ran `build.sh --project crm-system` and shipped 12 boss HTMLs. Every check I performed at the time said "all good":

| Check | Result | Reality |
|-------|--------|---------|
| Build exit code | 0 | 0 (build never fails on missing JSON) |
| `ls docs/_html/*-boss.html \| wc -l` | 12 | 12 (correct count) |
| `wc -c *.html` | ~20.6 KB each | All files have similar size regardless of content |
| `grep -l 'boss-placeholder' file.html` | All 12 matched | All 12 had the CSS class definition in `<style>` — false positive on EVERY file |

Then David opened one in his browser and said:

> "docs/_html 裡的boss.html 都好好，但有兩三個都沒有資料了"

Auditing the actual body content, **10 of the 12 were rendering the literal**:

```html
<div class="boss-placeholder">
  <h2>👀 老闆版摘要待生成</h2>
  <p>未有 <code>docs/_meta/api.json</code>，亦無 MD 內 <code>## 👀 老闆版摘要</code> 覆寫。</p>
  <p>請由 Developer profile (或 kanban CEO worker) 生成 boss summary JSON...</p>
</div>
```

Only 2 of 12 (PRD-boss, DESIGN-boss) had real content — those were the only two with a corresponding `docs/_meta/*.json` file. The other 10 were placeholders, all generated by the same `build.sh` run that exited 0.

## The false-positive grep footgun

My first audit reported **all 12 files as placeholders** because I grepped the WHOLE file:

```bash
grep -c 'boss-placeholder' docs/_html/api-boss.html
# 5  ← matches CSS class definitions in <style>
```

Then I did a "better" grep and reported **2 of 12 had content**, same false positive in reverse — the `class="boss-placeholder"` literal only appears in the body for genuinely-placeholder files, but `.boss-placeholder` (without the `class="`) appears in the CSS for ALL files. Depending on the regex flavor, the count came out 5-12.

**The verification that actually works** — extract the BODY region only (between `</head>` and `<script>`):

```bash
awk '/<\/head>/,/<script>/' docs/_html/api-boss.html | grep 'class="boss-placeholder"'
# (no output for content files; matches once for placeholder files)
```

This is now codified in `scripts/verify_boss_html.sh` which takes a project name and returns:
- **Exit 0**: all boss HTMLs have real content
- **Exit 1**: lists which boss HTMLs are placeholders
- **Exit 2**: build was never run

## The deeper lesson — step ordering

The skill's original "When to trigger" sequence was:

1. Write MD
2. Run build
3. Generate JSON (if missing)
4. Re-run build

This was wrong. Step 3 is opt-in behavior — I (the agent) noticed the missing JSONs and **skipped** generating them because there was no alarm in step 2. The build happily produced 12 placeholder HTMLs and exited 0. The agent's natural check ("does the build look healthy?") passed.

**Correct sequence**:

1. Write MD
2. **Generate JSON first** (or alongside MD, in the same LLM call)
3. Run build ONCE
4. **Verify with `verify_boss_html.sh`** — non-negotiable

The new SKILL.md "When to trigger" section encodes this, and `verify_boss_html.sh` is the gate that catches failures before they reach David.

## Who should generate the JSON — main agent vs CEO subagent

This was the second half of the lesson. My first instinct was to spawn a CEO subagent to write the 10 missing JSONs. But thinking about it:

- The CEO subagent gets only the MD content as input — no project history
- The MDs reference real incidents: "Prisma enum drift 導致 production 42704", "Bun 1.2 + Elysia bun build ReferenceError", "Hermes redact 機制 block smoke test output", "Migration sort pitfall"
- A subagent without conversation context would write generic risks ("technical debt", "scaling concerns", "user adoption risk") that David would immediately see as noise
- The MAIN agent has the full conversation context and can write concrete, project-specific risks that David recognizes as real

**Decision matrix** (now in SKILL.md "Generating the boss summary JSON"):

| Scenario | Recommended | Why |
|----------|-------------|-----|
| ≤ 5 docs, fresh project | CEO subagent | MD is sufficient context |
| 6+ docs, existing project with rich history | **Main agent directly** | Subagents hallucinate generic risks; main agent has real context |
| Mixed | Main for known, subagent for fresh | Per-doc decision |

I wrote all 10 JSONs directly in this session. David has not reviewed them yet — but they reference real incidents (Prisma enum drift, bun build pitfall, Hermes redact block, migration sort) that he will recognize, which is the test of a good boss summary.

## Take-aways for future sessions

1. **Never trust `build.sh` exit code alone for boss HTMLs.** Run `verify_boss_html.sh` after every build.
2. **Generate JSON before building, not after.** Reverse the step order.
3. **Body-region grep, not whole-file grep.** The CSS class definition `.boss-placeholder` will always be present in `<style>` and create false positives.
4. **Main agent vs subagent for JSON generation: pick by project size and history depth.** Subagents need a fresh slate; if you have the context, use it.
5. **File size is a trap.** 20 KB vs 24 KB is not visually distinguishable. Never rely on it.
