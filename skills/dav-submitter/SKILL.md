# Dav Submitter Skill

## 使用場景

在 SOP 的「提交成果」階段使用。當一個單元任務完成（可以是 User Story、子任務、Bug 修復、技術債處理等），Agent 必須立即產出交付摘要。

適用於：

- 讓用戶即時知道完成了什麼、有什麼價值
- 留下可追溯的交付歷史（特別是 Sprint Review、Module 交付時可一次過看所有 submission）
- 為下一個步驟（「重複第一步：溝通 & 思考」）提供輸入

**不適用於**：
- Sprint / Module 級別的宏觀總結（這屬於 `dav-reflection` 的範疇）
- 純粹提問 / 還沒執行任何任務的情況

## 觸發時機

| 情境 | 觸發 |
|------|------|
| 單元任務（US / 子任務 / Bug 修復）完成 | ✅ **必須觸發** |
| Sprint 結束 | ❌ 屬於 `dav-reflection` |
| Module 交付 | ❌ 屬於 `dav-reflection` |
| 純提問、未執行任務 | ❌ 不觸發 |

## 產出物（三層）

```
┌──────────────────────────────────────────────────────────┐
│  1. 對話中輸出簡單摘要                                       │
│     - 用了最簡單易明語法（對應 SOUL.md 原則）                   │
│     - 包含：完成什麼 / 對應 Backlog / 下一步建議              │
├──────────────────────────────────────────────────────────┤
│  2. Markdown 詳錄                                          │
│     路徑：docs/deliverable/<YYYY-MM-DD>-<task-slug>.md       │
│     - 完整結構化記錄                                        │
│     - 包含變更檔案、測試結果、AC 對應                          │
├──────────────────────────────────────────────────────────┤
│  3. HTML 視覺化版                                           │
│     路徑：docs/deliverable/<YYYY-MM-DD>-<task-slug>.html     │
│     - 給用戶最直觀看的版本                                   │
│     - 生動、可用 SVG 插圖                                    │
└──────────────────────────────────────────────────────────┘
```

## 命名規則

- **日期**：使用 ISO 格式 `YYYY-MM-DD`（Agent 執行當天）
- **task-slug**：用 kebab-case 英文，例如 `user-login-page`、`fix-cart-total-bug`、`refactor-auth-module`
- **範例**：`docs/deliverable/2026-01-15-user-login-page.md`

## 工作流程

```
┌──────────────────────────────────────────────────────────┐
│  1. 確認交付範圍                                            │
│     - 對應哪個 Backlog item（US / DE / TECH / Spike ID）     │
│     - 對應哪個 Sprint / Module                               │
│     - 收集這次的所有變更（檔案、測試、文檔）                     │
├──────────────────────────────────────────────────────────┤
│  2. 在對話中輸出簡單摘要                                     │
│     - 90 秒內能讀完                                         │
│     - 包含：做了什麼 / 為什麼 / 下一步                        │
│     - 保持簡單、不冗長                                       │
├──────────────────────────────────────────────────────────┤
│  3. 寫 Markdown 詳錄                                       │
│     - 套用 [[template.md]] 模板                              │
│     - 包含：交付摘要 / 變更檔案 / 驗收對應 / 已知問題 / 下一步  │
├──────────────────────────────────────────────────────────┤
│  4. 寫 HTML 視覺化版                                        │
│     - 套用 [[template.html]] 範例                            │
│     - 加入 SVG 插圖（圖標、流程、進度條）                      │
│     - 確保用戶即使不懂技術也能看懂                            │
├──────────────────────────────────────────────────────────┤
│  5. 確認下一步 / 回到 SOP 第一步                             │
│     - 提示用戶：下一步溝通要做什麼                            │
│     - 提供下一步的具體選項                                    │
└──────────────────────────────────────────────────────────┘
```

## 對話摘要 vs 文檔摘要的差異

| 項目 | 對話摘要 | Markdown / HTML 文檔 |
|------|---------|---------------------|
| 長度 | 短（90 秒可讀完） | 完整 |
| 目的 | 即時通知用戶 | 留底、可追溯 |
| 細節 | 重點結果 | 變更檔案、測試、AC 對應 |
| 視覺 | 純文字 + emoji | HTML 可有插圖 |
| 存檔 | 不存 | 永久保存 |

## 撰寫原則

- **簡單易明**：對應 SOUL.md「用最簡單易懂的語法，講得到複雜的事情」
- **有承擔**：好壞結果都是自己的，要誠實
- **有遠見**：下一步建議要有延伸性、Think Big
- **不重複**：對話摘要說過的，文檔不必重複；但文檔要包含對話沒說的細節
- **可追溯**：每個 production 都要對應 Backlog ID

## 與其他 Skill 協作

```
dav-planner     →  取得原始需求和痛點（用於「為什麼做」）
dav-designer    →  取得 docs/DESIGN.md 和模組劃分（用於對應 AC）
dav-reflection  →  取得技術債和問題（轉化為下一步 Action Items）
```

## 注意事項

- **不要過度包裝**：摘要的目的是溝通，不是炫技
- **不要省略了下一步**：這是 submitter 最重要的部分
- **不要寫假完成**：如果只完成一部分，要明確標註部分完成
- **保持順序穩定**：對話摘要 → Markdown → HTML，三者結構一致
