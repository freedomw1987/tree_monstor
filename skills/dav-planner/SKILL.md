# Dav Planner

## TL;DR

1. **做什麼**：把用戶的模糊需求，透過多輪提問 → SWOT（如需要）→ 7 個維度展開 → 寫成可執行的 `docs/backlog.md` User Story（含 AC 範本）。
2. **何時觸發**：用戶提出新需求 / 模糊想法 / 待辦項目 / 任務拆分。
3. **預設 SOP 路徑**：§2.1 Plan Gate（在 §2.0 啟動後、§2.2 Design 前）。
4. **關鍵紀律**：
   - **V01**：一次一個問題（不一次問 4 個）
   - **V02**：方案必標推薦（⭐ 必為第一個）
   - **V03**：SOP 修改必走 Reviewer 二審
5. **必產出物**：
   - `docs/backlog.md` 新增 row + 詳細段
   - `docs/ac/<US-ID>.md`（含 Given-When-Then + DoD）
   - `docs/ac/<US-ID>.html`（列印友好版）

## 觸發時機

| 情境 | 觸發 |
|------|------|
| 用戶提出新需求 | ✅ 必須 |
| 用戶提出模糊想法 | ✅ 必須 |
| 用戶列出待辦項目 | ✅ 必須 |
| 用戶要求任務拆分 | ✅ 必須 |
| 任務已執行（要交付）| ❌ 走 dav-submitter |
| 純粹閱讀 / 查資料 | ❌ 不觸發 |
| 純粹提問（沒要做）| ❌ 不觸發 |

## §2.7 用戶背景收集（v1.9 新增）

> **首次對話**：先問「你在這個項目的角色是？」，依角色動態追問；後續輪詢可跳過（依 §2.7.1 規則）。

### §2.7 角色 → 下一題對應表

| 用戶選 | Agent 下一題 |
|--------|-------------|
| **PM/PO** | 這項目的目標用戶是誰？規模（DAU/MAU）？ |
| **開發者** | 你熟悉的技術棧是？團隊規模？ |
| **設計師** | 有品牌規範 / 色票 / 字型嗎？視覺風格偏好？ |
| **業務/客戶** | 目標市場是？付款 / 物流偏好？ |
| **其他** | 請簡單描述你在這項目的角色 |

### §2.7.1 何時跳過角色題（極少數情境）

符合下列任一項可跳過，**且 Agent 必須明示跳過**：

1. 同一 User Story 第 3 輪以後（用戶已表明角色）
2. 用戶自我介紹中已表明角色（例如「我是這專案的 PM」）
3. 用戶明確說「直接問需求」

### §2.7.2 與 §3 Persona 補充維度區分

| 維度 | 對象 | 用途 |
|------|------|------|
| §2.7 角色 | **對話用戶**（跟你對話的人）| 調整提問深度與語言 |
| §3 Persona | **產品目標用戶**（產品給誰用）| 產品設計、UX 決策 |

## 流程（5 階段）

### Step 1：收集用戶背景（v1.9）

- **動作**：見上方 §2.7，依角色動態追問
- **為什麼**：調整後續提問深度（PM 不問技術棧、開發者不問品牌規範）
- **產出**：對話中知道用戶角色
- **證據**：對話有「角色 = X」字樣

### Step 2：提問技巧（V01 / V02 / §2）

- **動作**：依 §2.1 問題類型 / §2.2 選項設計 / §2.3 追問節奏；V01 一次一題、V02 推薦放第一
- **為什麼**：避免一次問太多、用戶選擇困難
- **產出**：對話中每輪 1 題 + 2-4 個選項
- **證據**：對話格式符合 V01/V02

### Step 3：決策點判斷（§2.5 / §2.6）

- **動作**：判斷是否任務升級（§2.5）、是否觸發 SWOT（§2.6）；如觸發則 Agent 草案 → 用戶驗證
- **為什麼**：避免「為分析而分析」、減少用戶決策負擔
- **產出**：對話中明示「是否升級 / 是否 SWOT」
- **證據**：對話有決策說明

### Step 4：7 個維度展開（§3）

- **動作**：核心 4 維度（必問）+ 補充 5 維度（視情境展開）
- **為什麼**：7 維度是「真實需求」完整性檢驗
- **產出**：對話中 4+ 維度都有對話
- **證據**：對話覆蓋核心 4 維度

### Step 5：成熟度評估 + 寫 Backlog（§5 / §4）

- **動作**：跑成熟度評估（涵蓋率 / 清晰度 / 可行性），3 維度都 ≥ 2 分才寫 Backlog
- **為什麼**：避免「需求不明就寫 US」
- **產出**：`docs/backlog.md` 新 row + 對應 `docs/ac/<US-ID>.md` + `.html`
- **證據**：成熟度評估表 + 3 檔都建立

## 規則 / 例外 / 限制

| 規則 | 例外 | 限制 |
|------|------|------|
| 一次只問 1 題（V01）| 確認型問題可一次多個 | 開放式問題必 1 題 |
| 方案必標 ⭐ 推薦（V02）| 開放式問題無推薦 | 必為第 1 個選項 |
| SOP 修改走 Reviewer 二審（V03）| 小型文字修正可跳 | 新增章節必走 |
| SWOT 不輕易觸發（§2.6）| 4 觸發條件之一即觸發 | 不可「為 SWOT 而 SWOT」 |
| AC 欄位精簡為「摘要 + 連結」（v1.8）| 存量 US 不重寫 | 新 US 必走新格式 |
| 反思併進 deliverable.md（v2.0）| 存量反思檔保留 | 未來不寫獨立反思 |
| 3 維度都 ≥ 2 分才寫 Backlog（§5）| 1 分項加 ⚠️ 註明 | 0 分項不可寫 |
| 每個 US 都產 .md + .html（同 turn）| 存量 US 不補 | 新 US 必走 |
| AC 範本只含 AC（不重複 US 標題）| N/A | §4.3.2.3 規範 |

## 提問技巧細節（§2 完整版）

### §2.1 問題類型

| 類型 | 何時用 | 範例 |
|------|--------|------|
| 開放式 | 探索未知領域 | 「你想要什麼效果？」 |
| 封閉式 | 確認 / 收斂 | 「A 還是 B？」 |
| 二選一 | 強烈對比 | 「用方案 A 還是 B？」 |
| 多選題 | 多種可能 | 「你想做 X / Y / Z 哪些？」 |

### §2.2 選項設計原則（V02 執行細節）

- 必含「⭐ 推薦」標示，且放第 1 個
- 選項 2-4 個（不超過 4）
- 描述必含「做了會發生什麼」+ 「為什麼這個」
- 不可隱藏用戶可選的「其他」（用 Type something）

### §2.3 追問節奏

- 開放式 → 封閉式 → 二選一（漸進收斂）
- 每輪結束必總結「目前已知」
- 避免「為追問而追問」（3-5 輪內收斂）

### §2.4 常見陷阱（自我檢查清單）

- ❌ 一次問 4 個問題
- ❌ 假裝完成（用戶還沒驗收就寫 Backlog）
- ❌ 過度分析（為分析而分析）
- ❌ SWOT 在不該用時強用
- ❌ 假設用戶懂技術術語

### §2.5 何時要任務升級（強制條款）

- 觸發條件：超出 dav-planner scope（用戶要做程式修改 / 系統部署）
- 動作：明示「這超出我的 scope，建議走 §2.3 Execution」

### §2.6 SWOT 分析決策點

- **觸發條件**（符合任 1 個即觸發；OR 不是 AND）：
  - 用戶表達強烈不確定（「不確定」「考慮中」「猶豫」）
  - 多方案競爭（3+ 候選方案）
  - 高風險 / 高成本決策
  - 用戶明確要求
- **不該觸發**：已有明確方向、簡單任務、時間緊急
- **4 象限標準格式**：S（優勢）/ W（劣勢）/ O（機會）/ T（威脅）各 1 行，每象限 ≤ 20 字

## 7 個維度（§3 完整版）

### 核心 4 維度（必問）

1. **用戶與場景** — 誰用？什麼情境？
2. **目標與痛點** — 為什麼做？解決什麼？
3. **流程與操作** — 怎麼用？流程？
4. **成功標準** — 怎麼算「做對了」？

### 補充 5 維度（視情境展開）

5. **Non-goals** — 不做什麼？
6. **Persona** — 目標用戶輪廓
7. **Edge cases** — 邊界情況
8. **Risks** — 風險
9. **Open questions** — 待釐清問題

## Backlog 規則（§4 完整版）

### §4.1 INVEST 原則

- **I**ndependent — 獨立
- **N**egotiable — 可協商
- **V**aluable — 有價值
- **E**stimable — 可估算
- **S**mall — 小
- **T**estable — 可測試

### §4.2 AC 範本（Given-When-Then / DoD）

- **Given-When-Then**：3 條以上 BDD 格式
- **DoD**：技術視角（4-6 項 checklist）

### §4.3 Backlog 編寫方式

- 表格欄位：US ID / 類型 / 標題 / AC / 優先級 / Story Point / 狀態 / 依賴
- 詳細段：放在表格下方（## TMO-XXX 詳細）
- 既有 US 不主動遷移；新 US 走新格式

### §4.4 類型混合管理

- User Story（新功能）/ Defects（Bug）/ Technical Debt（技術債）/ Spike（研究）
- 頂部精細、底部粗略（Granularity）

### §4.5 Backlog 更新規則

- 每一個項目目錄只有並唯一有一份 `docs/backlog.md`
- 每次新 Backlog item 填到表格最下方，不估算 / Sprint / Module，預設 PENDING

### §4.6 AC 範本生成 SOP（v1.8 新增，含 HTML）

- **生成時機**：用戶確認新 US 後、寫進 backlog.md 之前
- **生成順序（同 turn）**：先 .md → 再 .html → 最後更新 backlog.md
- **為什麼同 turn**：避免 .md 與 .html 不同步
- **過渡期規則**：既有 US（§4.3.2 之前）不主動生成 AC 範本
- **自我檢查清單**：5 項（檔案存在 / 連結路徑 / CSS 媒體查詢）

## §5 需求成熟度評估（寫 Backlog 前必跑）

| 維度 | 0 分 | 1 分 | 2 分 | 3 分 |
|------|------|------|------|------|
| **涵蓋率** | 只講 1 個維度 | 講 2~3 維度 | 講核心 4 維度 | 講核心 4 + 補充 ≥ 3 維度 |
| **清晰度** | 抽象 | 部分具體 | 全部具體但沒量度 | 全部具體 + 可量度 + 可觀察 |
| **可行性** | 沒考慮技術風險 | 有想過但沒驗證 | 已做 Spike 或有把握 | 已有 prototype 或現成方案 |

**規則**：
- 3 維度都 ≥ 2 分 → 可寫 Backlog
- 任一維度 = 0 分 → 必須繼續提問
- 任一維度 = 1 分 → 可寫但備註 ⚠️「成熟度不足」
