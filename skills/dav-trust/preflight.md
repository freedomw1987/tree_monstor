# Dav Trust — Preflight（啟動前檢查 + 執行期最小設計）

> 本檔為 dav-trust v2.3 新增子檔。引用：`SKILL.md` §Step 2「前置條件」+ §規則「規劃 / 設計階段不得在 trust 內執行」「執行期設計缺口只補最小技術契約」
>
> 主檔只保留 Step 2 簡述；完整判準、拒絕啟動話術、最小設計邊界都在本檔。

## §1 為什麼需要 preflight

規劃與設計兩階段在設計上**必須**與用戶互動：

- 規劃（dav-planner）：多輪提問釐清背景 / 目的 / 驗收標準；任一維度 0 分必須繼續提問
- 設計（dav-designer）：互動原型出爐前必走「設計自審 + 用戶簽核」，未簽核不進下一步

兩者都與 trust 的「中途不問用戶」直接互斥。所以 trust 不是「把 SOP 從頭跑一遍」，而是**只跑執行段**；
規劃 / 設計是 trust 的**前置條件**，必須在用戶在場時先完成。

**因此：能不能啟動 trust，必須在啟動前判斷 —— 事後發現做不到就已經浪費了整段 deadline。**

## §2 啟動前檢查（3 項；缺 deadline 先問一次，缺 backlog / 設計全缺才拒絕啟動）

| # | 檢查項 | 判準 | 不過的處置 |
|---|--------|------|-----------|
| 1 | **大目標 + Deadline 明確** | 用戶給了明確交付物 + 時間（相對時間也可，錨點由本 skill 解析） | 缺 → 問一次（唯一允許在啟動前打斷的情形）|
| 2 | **既有 backlog 可執行** | 已有 User Story：編號 + 驗收標準 + 狀態 | 缺 → **拒絕啟動**，請用戶先完成規劃階段 |
| 3 | **設計覆蓋** | 目標 US 已有對應設計（模組設計文件 / 技術方案）| 全缺 → **拒絕啟動**（唯一例外：用戶覆核 → §3.2）；部分缺 → 可啟動，缺口走 §4 執行期最小設計 |

**為什麼 backlog 缺就拒絕、而不是代答補齊**：
代答產生的 US 沒有驗收標準 = 無法驗收 = 做完也不知道對不對，等於白燒 deadline。
backlog 缺失是「規劃工作」，規劃工作需要用戶 —— 這正是 trust 不做的事。

## §3 拒絕啟動話術

### 3.1 backlog 缺（沒有可執行的 User Story）

```
⚠️ 無法啟動 Trust Mode：規劃 / 設計尚未完成

缺少: backlog（沒有可執行的 User Story）
需要: 先完成規劃階段（多輪提問釐清需求與驗收標準）

請先跑規劃，完成後再對我說「trust mode 跑 X，deadline Y」即可。
```

### 3.2 設計全缺（backlog 有、但無任何設計）

```
⚠️ 無法啟動 Trust Mode：目標 US 沒有設計

缺少: 設計（US-101 / US-102 / US-103 皆無對應設計）
需要: 先完成設計階段（模組設計 + 技術方案）

請先完成設計，完成後再對我說「trust mode 跑 X，deadline Y」即可。
```

> **Agent 端沒有繞道**：最小技術契約只適用於「部分缺」（某個 US 的設計缺）。
> 全缺 = 連 US 範圍都沒界定 → 最小技術契約無從下手。
> **唯一例外（用戶覆核）**：必須先輸出 §3.2 話術告知風險 → 等用戶**明確回覆**後才可啟動（不可由 Agent 自作主張）。
> 啟動後：① trust-log 必記 `📝 用戶覆核：設計全缺啟動`（用戶承擔風險）；
> ② 逐 US 走「執行期最小技術契約」補齊設計來源（§4 適用範圍因此擴為：全缺 + 用戶覆核）；
> ③ 該覆核只影響本次啟動，不改寫 §2 判準。
> **注意**：拒絕啟動 = trust 未進入 = 普通對話模式。此時**可以正常與用戶互動**（規劃階段本來就要互動），
> 不受「不問用戶」限制 —— 那條紀律只在 trust 已啟動後生效。

## §4 執行期最小設計（設計缺口補救）

只在「backlog 有、某個 US 的設計缺」、「L3 擴量產生的新 US（無設計）」或「設計全缺 + 用戶覆核（見 §3.2）」時啟用。目的是讓 Agent 能動手寫碼，但**不製造無人簽收的產物**。

| 允許做 | 不允許做 |
|--------|---------|
| 資料模型（欄位 / 型別 / 關聯）| 互動 HTML 原型 |
| API 介面（method / path / request / response）| UX 流程圖 / 線框圖 |
| 技術棧選型（沿用專案既有棧優先）| 完整 PRD 文件 |
| 錯誤處理策略、檔案 / 模組結構 | 視覺設計（配色 / 字體 / 間距）|
| 邊界情境清單（空值 / 權限 / 逾時）| 任何需要用戶簽核才有意義的產物 |

**為什麼不做原型 / PRD**：那兩類產物在流程上的價值來自「用戶簽核」，trust 產出無人簽收，
只會製造「看起來完成」的假進度 —— 屬於偽裝完成。

### 4.1 trust-log 記錄格式（時間戳沿用 time-anchor.md §3 絕對時間戳）

```markdown
## 2026-10-23 14:31:08 +0800 — 執行期最小設計（US-104）

**問題**：US-104 缺設計文件
**決策**：補最小技術契約 — 資料模型 + API 介面（略過互動原型 / 完整 PRD）
**理由**：trust 內無法取得用戶簽核，原型需待用戶在場時補
**可推翻**：✅
**事後待補**：互動原型、完整 PRD（trust 結束後由用戶決定是否補）
```

## §5 交接（trust 結束後）

| 事項 | 處置 |
|------|------|
| 走最小技術契約的 US | backlog 標 ✅ 已實作 + 附「待補產物：互動原型 / PRD」→ 列入 deliverable 的**待補清單**（不是未完成清單）|
| 因設計缺口而完全未實作的 US | backlog 標 ⏸️（待補設計）+ 列入 deliverable 的**未完成清單**；此類 ⏸️ 不進 L2 重訪 |
| L3 擴量新 US | 同上二列：走最小技術契約 → ✅ 已實作 + 待補產物清單；無法界定範圍 → ⏸️ |
| 互動原型 / PRD | 不主動補；用戶說「補設計」才走設計階段（正常互動流程）|
| 規劃 / 設計延後 | 用戶說「trust 結束後再規劃 / 補設計」→ trust 結束後再啟動對應階段（trust 內一律不跑）|
| need-you-help.md 的「改設計」抉擇 | 由用戶在 trust 結束後逐題回覆（走 ask-me 流程）|
| trust-log 的最小設計決策 | 可推翻：✅ —— 用戶可指定改成另一種技術方案 |
