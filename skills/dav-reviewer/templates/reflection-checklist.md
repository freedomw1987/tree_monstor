# 反省檢查清單

> 本檔係**可填充嘅反省檢查清單模板**（直接抄落交付摘要嘅「## 反思」段）。
>
> 本文件列出 6 項檢查維度的詳細檢查問題，供 Agent 在執行反省時逐項檢視。
>
> **點解要做**：交付咗 ≠ 交付得好；6 維度係檢驗「交付物是否真的好」嘅核心（宏觀層面，唔重複個別 US 嘅驗收）。

## 共通標記標準（6 維度共用）

- **✅ 通過** — 通用語意：該維度嘅檢查問題全部通過（**各維度嘅 ✅ 定義唔同**，見各節）
- **⚠️ 有風險** — 通用語意：有細問題，但不影響核心流程 / 核心價值
- **❌ 不通過** — 通用語意：有嚴重問題，或有用戶明顯不滿意的設計 / 阻礙開發的重大問題

> ⚠️ **⚠️／❌ 嘅「數量門檻」各維度唔同**（例如技術債係 1-3／4+、測試覆蓋率係 60-80%／<60%、RWD 係「小尺寸問題」／「完全不能用」）
> → **逐維度門檻見各節末嘅「門檻」行**，唔好套用通用標準。

## 1. UX/UI 一致性

**檢查目標**：確保實際交付的 UX/UI 符合用戶原本的需求意圖，並與 docs/DESIGN.md 規範一致。

- [ ] 是否所有畫面都符合 `docs/DESIGN.md` 規範（顏色、字體、間距、組件）？
- [ ] 是否有用戶原本沒要求、但我們自行加入的元素？
- [ ] 是否有原本用戶要求、但我們沒實現的元素？
- [ ] 互動流程（按鈕、導航、表單）是否符合用戶描述的操作路徑？
- [ ] 錯誤狀態（空狀態、錯誤提示、加載狀態）是否都有合適設計？
- [ ] 文案用語是否符合用戶的語言習慣（粵語／普通話／英文）？
- [ ] 圖示和圖片是否符合用戶業務場景？

**門檻**：⚠️ 1-2 項小問題｜❌ 3 項以上，或用戶明顯不滿意的設計

## 2. RWD 響應式設計

**檢查目標**：確保在桌面、平板、手機等不同尺寸下都能正確呈現。

- [ ] 桌面尺寸（≥1280px）是否正常？
- [ ] 平板尺寸（768px ~ 1279px）是否正常？
- [ ] 手機尺寸（<768px）是否正常？
- [ ] 字體大小在小螢幕是否仍可閱讀？
- [ ] 按鈕和點擊區域在手機上是否足夠大（建議 ≥44px）？
- [ ] 表格、表單在窄螢幕是否合理處理（橫向滾動或欄位調整）？
- [ ] 圖片是否有響應式處理（srcset、picture、不同尺寸）？
- [ ] 導航欄在小螢幕是否合理（漢堡選單或其他方案）？
- [ ] 是否考慮橫向／縱向螢幕切換的體驗？

**門檻**：⚠️ 1-2 個小尺寸問題（可手動避開）｜❌ 有尺寸完全無法使用，或核心功能在小螢幕失效

## 3. 技術債（Technical Debt）

**檢查目標**：找出會拖慢後續開發、增加維護成本的技術問題。

- [ ] 是否有硬編碼（魔術數字、hardcoded string）？
- [ ] 是否有重複代碼（DRY 原則違反）？
- [ ] 是否有過大的函數或組件（>300 行 / 過多職責）？
- [ ] 是否有過時的依賴或棄用的 API？
- [ ] 是否有缺少錯誤處理的地方（try/catch、邊界情況）？
- [ ] 是否有過度設計（YAGNI 違反）？
- [ ] 是否有缺少文件註解的關鍵邏輯？
- [ ] 環境變量和配置是否妥善管理？
- [ ] 是否有 TODO、FIXME、XXX 等未完成標記？

**門檻**：⚠️ 1-3 個輕微技術債｜❌ 4 個以上，或有阻礙開發的重大問題

## 4. 可維護性

**檢查目標**：確保代碼結構清晰，未來易於修改、擴展、除錯。

- [ ] 命名是否語意化（變數、函數、類別、文件）？
- [ ] 模組職責是否清晰單一（Single Responsibility）？
- [ ] 模組間耦合度是否過高？
- [ ] 是否有適當的抽象層（interface、type、abstract class）？
- [ ] 是否有清晰的目錄結構？
- [ ] 是否有 unit test、integration test 覆蓋？
- [ ] 第三方依賴是否合理（不過多、不過時）？
- [ ] 配置文件是否清晰、可維護？

**門檻**：⚠️ 有部分結構問題但不影響主要功能｜❌ 代碼結構混亂，未來修改成本高

## 5. 測試覆蓋率

**檢查目標**：確保每個驗收條件都有對應測試，且測試有效。

- [ ] 每個 User Story 的 AC 是否都有對應的測試用例？
- [ ] 是否有 unit test、integration test、E2E test 的分層？
- [ ] 測試覆蓋率是否達到合理水平（建議 ≥80%）？
- [ ] 是否有回歸測試（regression test）防止舊 bug 重現？
- [ ] 測試是否獨立、可重複執行？
- [ ] 是否有 mock、stub 處理外部依賴？
- [ ] CI/CD 是否整合自動測試？
- [ ] 是否有 flaky test（不穩定的測試）？

**門檻**：⚠️ 覆蓋率 60-80%，或缺少部分測試類型｜❌ 覆蓋率 <60%，或有 AC 沒對應測試

## 6. 需求對齊

**檢查目標**：確保實際交付真的解決用戶原本的痛點和目的。

- [ ] 實際功能是否解決 `docs/backlog.md` 中記錄的用戶痛點？
- [ ] 是否有原本用戶描述的需求被遺漏？
- [ ] 是否有原本用戶沒要求、但被加入的功能（scope creep）？
- [ ] 用戶的原始目的是否真正達成？（不是 only 完成任務，而是達成目的）
- [ ] 是否有需要跟用戶再確認的模糊需求？
- [ ] 交付價值是否符合用戶預期？
- [ ] 驗收條件是否真的被滿足？

**門檻**：⚠️ 有小偏差但不影響核心價值｜❌ 偏離用戶原本目的，或有重大遺漏

## 使用方式

1. 依序檢查 6 個維度，每個維度逐項回答檢查問題
2. 標記 ✅ / ⚠️ / ❌
3. 對於 ⚠️ 和 ❌ 的項目，記錄具體問題和建議改善方案
4. 將問題轉化為 Backlog item，更新到 `docs/backlog.md`
5. 將完整結果輸出到反省報告（模板見同套 `./reflection-templates.md`）

## 7. jev_judge 對接表（v2.1 新增）

本表把 6 個維度的檢查問題對應到 `jev_judge` 的問題模板，供 agent 在 `JEV_AVAILABLE=true` 時批次評分。

- **UX/UI 一致性** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物的 UX/UI 是否符合 docs/DESIGN.md 規範且無 scope creep？」；信心低時 escalate
處理：⚠️ 標待確認、列 **deliverable.md `## 反思` 段的「⚠️ jev escalate 待確認」清單**（不寫在本檔）
- **RWD 響應式設計** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物在桌面/平板/手機三尺寸下是否都能正常使用？」；信心低時 escalate 處理：⚠️ 標待確認、列
deliverable.md `## 反思` 段
- **技術債** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物是否有 4 項以上技術債（魔術數字 / DRY 違反 / 過時依賴 / 缺錯誤處理）？」；信心低時 escalate 處理：⚠️
標待確認、列 deliverable.md `## 反思` 段
- **可維護性** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物的代碼結構是否清晰、未來修改成本低？」；信心低時 escalate 處理：⚠️ 標待確認、列 deliverable.md
`## 反思` 段
- **測試覆蓋率** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物的測試覆蓋率是否 ≥80% 且每個 AC 都有對應測試？」；信心低時 escalate 處理：⚠️ 標待確認、列
deliverable.md `## 反思` 段
- **需求對齊** — jev_judge 問題模板（score 類型，三檔 ✅/⚠️/❌）：「這個交付物是否真正解決用戶痛點、無遺漏、無過度？」；信心低時 escalate 處理：⚠️ 標待確認、列 deliverable.md
`## 反思` 段

**使用方式**：

- agent 在 Step 2 對 6 個維度做 LLM 自評時，**同時**對每個維度跑一次 `jev_judge`（一個 batch call、score 類型）
- US 級別輕量路徑（S2）：只打「需求對齊」+「測試覆蓋率」兩個關鍵維度
- jev 結果與 LLM 自評比對，不一致時以 LLM 為準、但 jev 結果附在反思段備註
- `escalate: true`（信心低）時，按上表處理：⚠️ 標待確認、列 deliverable.md，不在本檔

**術語對齊說明（B2）**：本 skill 只用 `score` 類型；dav-developer 用 `noul / choice / score` 三類混合（不同設計選擇）。
