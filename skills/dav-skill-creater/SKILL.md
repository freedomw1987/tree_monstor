# Dav Skill Creator

## TL;DR

1. **做什麼**：從用戶對話或操作中提煉可重複應用的概念 → 生成新 skill（含 frontmatter + 「任務導航」5 段結構）→ 存進 `skills/<name>/SKILL.md`。**同時也是「修改既有 skill」的規範權威**（v2.3）：任何 skill 修改必遵守本規範、必走修改流程。
2. **何時觸發**：用戶主動說「這是一個 skill」、「把它變成 skill」、「做 skill」；Agent 偵測到對話內容具備重複應用潛力。
3. **預設 SOP 路徑**：§2.6 一般任務（不需完整 SOP，因 skill 是輔助元工具）。
4. **關鍵紀律**：
   - **概念提煉 ≠ 操作記錄**：只總結「步驟描述 + 每步目的 + 想要效果」，不含具體代碼指令
   - **150 行上限**：SKILL.md 過長必拆到子檔（如 `examples.md`、`workflow.md`）
   - **「任務導航」5 段**（v2.1）：TL;DR / 觸發時機 / 流程 / 規則 / 變動歷史（推薦結構）
   - **純文字引用**（v2.1）：不放 `../`、`docs/` 跨檔連結或 `[[...]]` Obsidian cross-dir 連結；改用純文字「見 <path>」
   - **frontmatter 必填**：`name` + `description` 一句話 + 何時用 + 何時不用
5. **必產出物**：`skills/<name>/SKILL.md`（必含 frontmatter + 5 段結構）

## 觸發時機

| 情境 | 觸發 |
|------|------|
| 用戶說「這是一個 skill」「把它變成 skill」| ✅ 必須（新建）|
| Agent 偵測對話有可重複應用潛力 | ✅ 主動詢問用戶（新建）|
| 對話中出現「下次也這樣做」「之後再遇到」| ✅ 詢問是否變 skill（新建）|
| 純提問 / 不需重複應用 | ❌ 不觸發 |
| 用戶明確說「這不用記」 | ❌ 不觸發 |
| **用戶說「修改 skill」「重結構 skill」「改一下 SKILL.md」** | ✅ 必須（修改流程）|
| **Agent 接到任務修改任何 `skills/<name>/SKILL.md`** | ✅ 必走修改流程、遵守 v2.3 規範 |
| **既有 skill 探針 fail（規範偏差）** | ✅ 走修改流程修齊（不單純跳過）|

## 流程（5 步）

### Step 1：提煉概念

- **動作**：從對話 / 操作中提煉可重複應用的概念（工作描述 + 步驟 + 每步目的 + 想要效果）
- **為什麼**：skill 是「可重用的概念」，不是「操作記錄」
- **產出**：概念草稿（含描述使用場景）
- **證據**：能用 2-3 句話說明「下次遇到 X，會這樣做」

### Step 2：與用戶確認

- **動作**：詢問用戶 1）技能名稱（必英文字符或 kebab-case）2）使用場景描述 3）必含規則
- **為什麼**：避免 AI 自行命名、避免場景不清
- **產出**：對話確認三項
- **證據**：對話有「名稱 = X / 場景 = Y / 規則 = Z」

### Step 3：設計「任務導航」結構（v2.1）

- **動作**：依推薦結構組織 SKILL.md — TL;DR / 觸發時機 / 流程 / 規則 / 變動歷史
- **為什麼**：LLM 注意力優化 — 5 段結構讓 LLM 快速定位、降低認知負擔
- **產出**：SKILL.md 草稿
- **證據**：5 段齊全（每段有獨立 `## <name>` 標題）

### Step 4：寫入 SKILL.md（純文字引用）

- **動作**：寫入 `skills/<name>/SKILL.md`，含 frontmatter；過 150 行拆子檔（如 `examples.md`）
- **為什麼**：可讀性 + skill 獨立搬動（純文字引用允許 skill 移到任何位置仍可用）
- **產出**：`skills/<name>/SKILL.md` + 必要子檔
- **證據**：SKILL.md < 150 行（或有合理解釋）+ 純文字引用

### Step 5：自驗收

- **動作**：自己讀一次 SKILL.md、確認 1）frontmatter 齊全 2）5 段結構 3）150 行內 4）純文字引用 5）有一句話 description
- **為什麼**：skill 是「給 LLM 讀的」，可讀性差直接影響效果
- **產出**：自驗收通過
- **證據**：5 項檢查全綠

## 流程（修改既有 skill — v2.3 新增）

適用於「任何 `skills/<name>/SKILL.md` 被修改」的場景。不必從 0 建立，但要遵守同一套規範。

### M-Step 1：讀舊版 + 評估規範偏差

- **動作**：讀舊版 SKILL.md，依 v2.1（5 段結構）+ v2.2（純文字引用、跨目錄讀檔零容忍）+ v2.3（本版規則）列出規範偏差
- **為什麼**：避免修改過程中引入新規範違反舊偏差、避免「修一個錯就其他錯又出來」
- **產出**：規範偏差清單（每條：行號 / 違反哪條規則 / 建議改法）
- **證據**：清單列出所有偏差（含 0 偏差的「合規」情況）

### M-Step 2：套用變更（含規範偏差修正）

- **動作**：依用戶需求修改 SKILL.md，**同時修正規範偏差清單中的所有項**（不允許「修 A 順手保留 B 偏差」）
- **為什麼**：存量合規保證 — 修改一個 skill 的同時清除所有偏差，避免技術債累积
- **產出**：修改後的 SKILL.md
- **證據**：規範偏差清單全清、需求變更已套用

### M-Step 3：自驗收 + 探針驗證

- **動作**：自己讀修改後 SKILL.md、確認 1）需求變更已套用 2）規範偏差已修正 3）5 項檢查全綠 4）`bats tests/restruct-*.bats` 全綠
- **為什麼**：修改後驗證是保護既有探針不退化的關鍵
- **產出**：自驗收通過 + bats 全綠
- **證據**：5 項檢查全綠 + `bats tests/restruct-<skill-name>.bats` 全綠

**v2.3 紀律**：
- 修改流程不跳過規範偏差修正（不允許「修 A 留 B」）
- 修改後必須跑既有 `restruct-<name>.bats` 確認不退化
- 修改量大時考慮走完整 SOP（§2.1→§2.5）+ Reviewer 二審

## 規則 / 例外 / 限制

| 規則 | 例外 | 限制 |
|------|------|------|
| SKILL.md < 150 行 | 大型 skill（如 dav-planner）可例外 | 過長必拆 `examples.md` / `workflow.md` |
| frontmatter 必含 `name` + `description` | N/A | 不接受空 frontmatter |
| 概念提煉 ≠ 操作記錄 | N/A | 代碼示例放 `examples.md` |
| 5 段任務導航結構（v2.1）| 極簡 skill 可只有 TL;DR + 流程 | 推薦但不強制 |
| 純文字引用（v2.1）| skill 子檔可用 markdown | 不寫 `../`、`docs/`、`[[...]]` 跨 dir 連結 |
| 名稱必 kebab-case | N/A | 不接受空格、中文 |
| description 一句話 | N/A | 含「做什麼 + 何時用 + 何時不用」|
| 跨 skill 溝通純文字 | N/A | 用「見 <path>」 |
| **修改既有 skill 必走 v2.3 流程**（v2.3 新增）| 純錯字修正（如拼字）可跳過 | 修改 ≧ 3 行必走 M-Step 1-3 |
| **修改同時必清規範偏差**（v2.3 新增）| 用戶明確說「只修 A 不動 B」例外 | 不可「修 A 留 B 偏差」累积技術債 |
| **修改後必跑既有探針**（v2.3 新增）| 僅改探針本身（顯然要跑）| 退探即視為修改失敗 |
| **變動歷史外移至 `CHANGELOG.md`**（v2.4 新增）| 變動歷史 ≤ 3 條可留主檔 | 超過 3 條一律外移；主檔只留最近 3 條 + 引用 CHANGELOG.md |

## SKILL.md 編寫準則 + 變動歷史外移（LLM 注意力優化）

完整編寫準則見 [`editor-guide.md`](./editor-guide.md)（含 5 段結構、可讀性原則、反模式、純文字引用規範 v2.1+v2.2、變動歷史外移規範 v2.4）。

**本檔只列 3 條最高頻規則**（其他細節查 editor-guide.md）：

1. **5 段任務導航**：TL;DR / 觸發時機 / 流程 / 規則 / 變動歷史 — 5 段是 LLM 注意力優化推導出的最佳平衡
2. **變動歷史外移（v2.4）**：超過 3 條必外移至 `<skill>/CHANGELOG.md`（規範詳見 editor-guide.md）
3. **純文字引用（v2.1+v2.2）**：skill 內不放跨 dir 連結，連「見 + path」這類自然語言描述也不可；用抽象詞「見 monorepo 對應的 PRD 文件」

**例外**：skill 子檔之間（與 SKILL.md 同 dir）可用 markdown 相對連結。
