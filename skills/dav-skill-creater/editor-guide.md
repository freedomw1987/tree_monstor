# Editor Guide — SKILL.md 編寫準則

> 本檔為 dav-skill-creater 的「SKILL.md 編寫準則」章節（v2.1-v2.11 累積）抽出。
> 從 SKILL.md v2.5 起，本檔獨立。理由：編寫準則屬於「寫 skill 時才需要看」，不在「用 skill」的主流程上。

## 4 段推薦結構（任務導航）

- **TL;DR** — 目的：第一眼看到。寫法：5 個重點條列（做什麼 / 何時觸發 / SOP 路徑 / 關鍵紀律 / 必產出物）
- **觸發時機** — 目的：何時該用 / 不該用。寫法：列表（情境 ＋ ✅/❌）
- **流程** — 目的：怎麼做。寫法：N 步，每步 動作 / 為什麼 / 產出 / 證據
- **規則** — 目的：邊界 / 例外 / 限制。寫法：列表，每條規則 ＋ 例外／限制子項

> v2.1 原本 5 段（多「變動歷史」）→ v2.9 刪走（見下章）。

## 可讀性原則

- **TL;DR 必須第一**：讓 LLM 第一秒就抓到核心
- **emoji 限縮**：只在「觸發時機」用 ✅🟡❌，唔在流程／規則濫用
- **流程明步**：每步必含 動作 / 為什麼 / 產出 / 證據 四元素
- **規則用列表**：每條規則一個列表項 ＋ 例外／限制做子項（唔用三欄表）

## 反模式（避免）

- ASCII box-drawing 流程圖 → 改為：文字描述 ＋ 列表
- 一大段散文 → 改為：5 條列
- 不明步驟（只有標題）→ 改為：每步 4 元素
- 沒 frontmatter → 改為：必含 `name` + `description`
- `description` 太長（> 200 字）→ 改為：一句話聚焦 ＋ 何時用 ＋ 何時不用
- 跨 dir 連結（相對路徑指 docs/ 或 Obsidian wiki link）→ 改為：純文字「見 monorepo 對應的 PRD 文件」
- 主檔寫「變動歷史」版本表／另開 `CHANGELOG.md` → 改為：唔記（v2.9），演進靠 `git log skills/<name>/`

## 純文字引用規範（v2.1 + v2.2）

**v2.1 — markdown 跨 dir 連結零容忍**：不放 markdown 相對連結指本 skill dir 之外；不放 Obsidian wiki link 指其他 dir。skill 子檔之間可用 markdown
連結（同一 dir）。

**v2.2 — 跨目錄讀檔引用零容忍**（更嚴格）：
- 唔放「讀 + path」「見 + path」「詳見 + path」等指向本 skill 目錄以外檔案嘅引用（連自然語言描述都唔准）
- 唔放跨 skill 引用（指其他 skill 頂層 SKILL.md）；唔放指名 docs/ 內具體檔案
- 替代寫法：抽象詞「見 monorepo 對應的 PRD 文件」「見同套 other-skill 子檔」（由 monorepo 約定或同套安裝關係取得）
- **產出目的地（寫到 docs/）仍保留** — docs/ 係 project 約定、屬「寫到哪」語意，唔係讀檔引用

**為什麼更嚴**：skill 搬動到任何位置仍可運作，不依賴 monorepo 內 docs/ 或其他 skill 結構。

**Obsidian `[[xxx]]` 教學標記（v2.2）**：dav-wiki 等 skill 提到 Obsidian 雙向連結教學時，必加「`<教學範例>`」標記（例如「產出：教學範例：markdown 內 `[[xxx]]`
標記 — 實際 wiki 產出由 dav-wiki 處理」），避免讀者誤判為跨檔連結。

**例外**：AGENTS.md（全域索引）內嘅 handbook／gates.json 連結；skill 寫到 docs/（寫入目的地）。

## 變動歷史：唔記（v2.9）

**規則**：skill 主檔**唔寫變動歷史**（冇 `## 變動歷史` 段、冇版本表），亦**唔准新增** `CHANGELOG.md`。

**為什麼**（2026-10-27 減上下文決定）：變動歷史對「當下執行任務」冇直接幫助 → 稀釋主檔注意力、消耗 context；`CHANGELOG.md` 一個檔就係一份 context 成本，而 agent 觸發 skill
時**根本唔會讀** → 純維護面。演進嘅真實記錄**已經喺 git**（`git log --oneline -- skills/<name>/`）→ 唔需要第二份。

**硬規定**：任何 skill 都唔准再新增 `CHANGELOG.md`；主檔以外唔放變動歷史。

## 表格禁令（v2.10）

**規則**：skill 內（主檔 ＋ 支援子檔 ＋ **skill 生成嘅 markdown**）一律**唔用 markdown 表格**，改用**列表**（有序／無序 ＋ 縮排）。

**點解**：表格欄位窄，長句喺表內要換行／擠壓 → 手機同窄視窗難讀；表格要 `|` ＋ 分隔行 → token 成本高；表格只支援「同列欄位對齊」，跨行／跨段資料（例如「規則 → 例外 → 限制」三層）根本唔適合。

**點樣寫**：三欄表 → 每條規則一個列表項（`- **一次只問 1 題（V01）**` ＋ 子項 `- 例外：⋯` ＋ `- 限制：⋯`）；情境表 → 列表（`- **用戶提出新需求**：✅ 必須`）；欄位定義 →
逐行列表；多欄位資料 → 每個項目一個小節 ＋ 欄位列表。

**例外（必須保留表格嘅地方）**：
- 本 skill 自己嘅「格式範本」碼 block（示範用 markdown 原文）
- 目標專案端**被工具解析**嘅結構化資料檔 → 改格式 = 改契約，要另開票（唔可以喺呢度順手改）
- **資料表**（真係需要「同列比較」嗰啲：框架對照、AC 清單、資料矩陣）→ 保留表格，但每欄標題要自我解釋。⚠️ 「欄位定義」唔屬呢類 → 用列表

**存量 sweep（2026-10-27）**：批次 A 已完成（`skills/` ＋ `docs/sop/handbook/` 敘述性表全部改列表，0 個表殘留）；批次 B 保留表格（目標專案端被工具解析嘅結構化資料檔）；其餘
live .md 未 sweep（待辦）。新規則約束**新寫／改寫**嘅內容 —— 唔因為「存量未改」就當例外。

**自己生成嘅 markdown 要一致**：skill 唔准「自己用列表、生成嘅文件用表格」。

## 文檔行數限制（v2.11 減法版）

**為什麼**：agent 每次觸發 skill 都要把主檔（＋被指標指向嘅子檔）讀落 context；文檔愈長 → 注意力愈被稀釋、每次觸發嘅成本愈高。行數限制係**寫文件時嘅硬門檻**。

- **`SKILL.md`（主檔）：≤ 50 行**（硬上限）→ 超標必拆子檔：內容留子檔、主檔只留指標
- **支援子檔：≤ 150 行**（硬上限）→ 拆成兩份，或壓成清單
- **單一 skill 嘅 context 總量**（主檔 ＋ 全部支援 .md）：**≤ 400 行**（硬上限）→ 先做減法（去重 → 列表化 → 指標化），再考慮拆檔
- **例外（不計入上面任何上限、亦不計入 context）**：支援檔嘅路徑或檔名命中 `example` / `template` / `fixture` / `PoC` → 佢哋係**樣例資料、可填充模板、demo
實作**，唔係每次觸發都要讀嘅指引
  → ⚠️ 只可以真係樣例／模板用；**流程同規則內容唔准靠改名喺例外口徑下逃避限制**
- **新增支援檔** → **新增前必先問：可唔可以合併入現有子檔？**（淨係新檔 ＋ 新指標 ＝ context 成本淨增）

**點解廢走 baseline ratchet**：v2.8 用「每個 skill 各自 baseline，只可下唔可上」，但 11 個 skill 合計 8,395 行、平均 ~763 行 → 冇人跟得到 = **假規則**。→
v2.11 改用**絕對上限**（主檔 50／子檔 150／context 400）＋ 例外口徑（樣例唔計）。一個 skill 超上限 → 拆成兩個「專注一件事」嘅 skill，唔係登記例外。

**點樣量**：
- 主檔：`wc -l skills/<name>/SKILL.md`
- context：
`git ls-files skills/<name> | grep '\.md$' | grep -viE 'example|template|fixture|poc' | xargs -r cat | wc -l`（只計 git
  追蹤嘅檔；機械探針用 `find` → 連**未 commit** 嘅新檔都計 → 探針嚴過手量法，冇規則漏洞）
- 機械探針：`tests/skill-size.bats`（repo 級 → 逐個 skill 守上面 3 條上限 ＋ 例外口徑）

**點解要有機械探針**：v2.8 曾刻意「唔用探針守」（怕框架膨脹）→ 冇人跟 → 2026-10-28 實測：11 個 skill **全部**主檔超 50 行、7 支子檔超 150 行 → 規則失效。探針只「量行數」、唔解釋內容 →
成本低、唔會膨脹框架；而且令**之後新造嘅 skill 一樣受約束**。

## 行數預檢規範（改 skill 前必跑）

**同源**：AGENTS.md §1.5 的 V03（純 markdown 只自查行數上限；代碼／契約／探針先走二審）＋ 本檔的預檢規範。

**觸發條件**：任何 skill／SOP 檔案改動前 —— 純 markdown 改動 = V03 文件分支嘅唯一必檢項；代碼／契約／探針改動 = 走 Reviewer 二審之前嘅預檢。

**動作**（三條量法同一個管線，只係下游唔同）：

- **主檔 ≤ 50**：`wc -l skills/<name>/SKILL.md` → 若 > 50 → 必先瘦身
- **支援子檔 ≤ 150 ＋ context ≤ 400**：用下面同一條管線量（只係下游唔同）→ 任何一個 > 150 → 拆檔或壓成清單；context > 400 → 減法

```bash
LIST="git ls-files skills/<name> | grep '\.md$' | grep -viE 'example|template|fixture|poc'"
wc -l skills/<name>/SKILL.md            # 主檔行數
$LIST | xargs -r -n1 wc -l | sort -rn    # 每支子檔行數
$LIST | xargs -r cat | wc -l            # context 總量
```

- **覆驗**：改完跑 `bats tests/skill-size.bats`

**為什麼**：主檔 > 50 → 違反「主檔上限 50」（每次觸發都要讀）；子檔 > 150 → 違反「子檔上限 150」；context > 400 → 違反「單 skill context 上限 400」。

**例外**：純文字修正（typo / link / 註解）不需預檢。

## 探針修改比照 V03（原 V03.6，2026-09-26 新增）

**同源**：AGENTS.md §1.5 的 V03 **代碼分支**（改探針 = 改代碼 → 必走二審）。

`tests/**/*.bats` 同 `skills/*/tests/**/*.bats` 的修改**視同規範修改**（新增 / 刪除 / **條件放寬**），必走 V03 Reviewer 二審；純文字修正（typo / link /
註解 / 訊息文字微調）不觸發。修訂完成後、Reviewer 必附「`bats tests/<檔>` 跑動輸出」（修改前 fail / 修改後 pass 兩次輸出必貼）。

**「條件放寬」的定義**（符合任一即算）：① 讓原本會 fail 的情況改為 pass；② 檢查門檻變低（例如從「必須綠」改成「綠或黃」）；③ regex 從嚴變寬（例如從 `must contain X` 改成
`must contain X or Y`）。

嚴格化（`keep = pass → must pass`）屬規範強化，亦可走 V03 但非必走。
