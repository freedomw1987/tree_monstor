# Editor Guide — SKILL.md 編寫準則

> 本檔為 dav-skill-creater 的「SKILL.md 編寫準則」章節（v2.1-v2.2 累積）抽出。
> 引用：`SKILL.md` 的「SKILL.md 編寫準則」章節
>
> 從 SKILL.md v2.5 起，本檔獨立。理由：原本 60 行的編寫準則屬於「寫 skill 時才需要看」，不在「用 skill」的主流程上。

## 4 段推薦結構（任務導航）

- **TL;DR**
  - 目的：第一眼看到
  - 寫法：5 個重點條列：做什麼 / 何時觸發 / SOP 路徑 / 關鍵紀律 / 必產出物
- **觸發時機**
  - 目的：何時該用 / 不該用
  - 寫法：表格：情境 + ✅/❌
- **流程**
  - 目的：怎麼做
  - 寫法：N 步，每步 動作/為什麼/產出/證據
- **規則**
  - 目的：邊界 / 例外 / 限制
  - 寫法：列表：每條規則 ＋ 例外／限制子項（表格禁令 v2.10）

> v2.1 原本係 5 段（多一個「變動歷史」）→ **v2.9 刪走**：skill 唔記歷史變動（見下章）。

## 可讀性原則

- **TL;DR 必須第一**：讓 LLM 第一秒就抓到核心
- **emoji 限縮**：只在「觸發時機」表用 ✅🟡❌，不在流程 / 規則濫用
- **表格只放結論**：長說明放流程步驟內、不放表格
- **流程明步**：每步必含 動作 / 為什麼 / 產出 / 證據 四元素
- **規則用列表**：每條規則一個列表項 ＋ 例外／限制做子項（唔用三欄表）

## 反模式（避免）

- **ASCII box-drawing 流程圖**
  - ✅ 改為：文字描述 + 表格
- **一大段散文**
  - ✅ 改為：5 條列
- **不明步驟（只有標題）**
  - ✅ 改為：每步 4 元素（動作 / 為什麼 / 產出 / 證據）
- **沒 frontmatter**
  - ✅ 改為：必含 `name` + `description`
- **`description` 太長（> 200 字）**
  - ✅ 改為：一句話聚焦 + 何時用 + 何時不用
- **跨 dir 連結（相對路徑指 docs/ 或 Obsidian wiki link 指其他 dir）**
  - ✅ 改為：純文字「見 monorepo 對應的 PRD 文件」
- **主檔寫「變動歷史」版本表／另開 `CHANGELOG.md`**
  - ✅ 改為：唔記（v2.9）：演進靠 `git log skills/<name>/`

## 純文字引用規範（v2.1 + v2.2）

**v2.1 — markdown 跨 dir 連結零容忍**：
- **不放 markdown 跨 dir 連結**：禁止任何用相對路徑指向 SKILL.md 所在 dir 之外的 markdown 連結
- **不放 Obsidian 跨 dir 連結**：禁止用 Obsidian wiki link 指向其他 dir 的檔案
- **skill 子檔可用 markdown**：因為子檔和 SKILL.md 在同 dir，可正常使用相對連結

**v2.2 — 跨目錄讀檔引用零容忍**（更嚴格）：
- **不放跨目錄讀檔引用**：禁止任何「讀 + path」「見 + path」「詳見 + path」這類指向 skill 自己目錄以外檔案的引用（自然語言描述）
- **不放跨 skill 引用**：禁止任何指向其他 skill 頂層 SKILL.md 的引用
- **不放指向 docs/ 內具體檔案**：禁止任何指名 docs/ 子目錄內具體檔案的引用
- **替代寫法**：抽象詞「見 monorepo 對應的 PRD 文件」、「見 SOP 全域變動歷史」、「見同套 other-skill 子檔」（由 monorepo 約定或同套安裝關係取得）

**為什麼更嚴**：
- skill 搬動到任何位置仍可運作，不依賴 monorepo 內的 docs/ 或其他 skill 結構
- 產出目的地（寫到 docs/）仍保留 — docs/ 是 project 約定、屬於「寫到哪」語意
- 讀檔引用（從 docs/ 讀）破壞獨立性、寫到 docs/ 不破壞獨立性（LLM 仍可決定寫入路徑）

**Obsidian `[[xxx]]` 教學標記（v2.2）**：
- dav-wiki 等 skill 提到 Obsidian 雙向連結教學時，必加「`<教學範例>`」標記
- 例如：「產出：教學範例：markdown 內 `[[xxx]]` 標記 — 實際 wiki 產出由 dav-wiki 處理」
- 避免讀者誤判 `[[xxx]]` 為跨檔連結

**例外**（仍可用 markdown 連結 / 路徑引用）：
- `AGENTS.md`（全域索引、非 skill）內的 handbook / gates.json 連結
- skill 寫到 docs/（project 約定的寫入目的地）

## 變動歷史：唔記（v2.9）

**規則**：skill 主檔**唔寫變動歷史**（冇 `## 變動歷史` 段、冇版本表），
亦**唔准新增** `CHANGELOG.md`。

**為什麼**（2026-10-27 減上下文決定）：
- 變動歷史對「當下執行任務」冇直接幫助 → 只係稀釋主檔注意力、消耗 context
- `CHANGELOG.md` 一個檔就係一份 context 成本（13 個 skill × 平均 19 行 ≈ 250 行），
  而 agent 觸發 skill 時**根本唔會讀**佢 → 純維護面
- 演進嘅真實記錄**已經喺 git**（`git log skills/<name>/`）→ 唔需要第二份

**點樣查演進**：`git log --oneline -- skills/<name>/`（或該檔嘅 blame）。
**硬規定**：任何 skill 都唔准再新增 `CHANGELOG.md`；主檔以外唔放變動歷史。

## 表格禁令（v2.10 新增）

**規則**：skill 內（主檔 ＋ 支援子檔 ＋ **skill 生成嘅 markdown**）一律**唔用 markdown 表格**，
改用**列表**（有序／無序 ＋ 縮排）。

**點解**：

- 表格欄位窄，長句喺表內要換行／擠壓 → 手機同窄視窗好難讀
- 表格要 `|` ＋ 分隔行 → **token 成本高**（同一份資訊，列表更省）
- 表格只支援「同列欄位對齊」；跨行／跨段嘅資料（例如「規則 → 例外 → 限制」三層）根本唔適合

**點樣寫**（原本嘅表 → 改列表）：

- 「規則 / 例外 / 限制」三欄表 → 每條規則一個列表項，例外／限制做子項
  （`- **一次只問 1 題（V01）**` ＋ 子項 `- 例外：⋯` ＋ `- 限制：⋯`）
- 「情境 / 觸發」表 → 列表（`- **用戶提出新需求**：✅ 必須`）
- 欄位定義（要逐個欄位抄）→ 用列表逐行列出（`- **US ID**：⋯`）
- 多欄位資料 → 每個項目一個小節 ＋ 欄位列表（唔用一列一個項目嘅大表）

**例外**（必須保留表格嘅地方）：

- 本 skill 自己嘅「格式範本」碼 block（示範用嘅 markdown 原文）→ 跟目標專案格式
- 目標專案端**被工具解析**嘅結構化資料檔 → 改格式 = 改契約，要另開票（唔可以喺呢度順手改）
- **資料表**（真係需要「同列比較」嗰啲：框架對照、AC 清單、資料矩陣）
  → 改成列表反而**更難讀**（要逐個項對住欄位名讀）→ 保留表格，但每欄標題要自我解釋
  ⚠️ 注意：**欄位定義**唔屬呢類（「欄位：內容」逐行列出就夠）→ 照「點樣寫」嗰段用列表

**存量 sweep 進度**（2026-10-27）：

- **批次 A（已完成）**：`skills/` ＋ `docs/sop/handbook/` 嘅敘述性表全部改成列表（0 個表殘留）
- **批次 B（保留表格，屬本節例外）**：目標專案端**被工具解析**嘅結構化資料檔
  —— `docs/backlog.md` 嘅 row 表、對帳表、PRD 追溯矩陣 → 改格式 = 改 doc-drift 解析器契約，要另開票
- 其餘 live .md（`docs/` 根層、`README.md`、`CONTRIBUTING.md` 等）→ 未 sweep，屬待辦

新規則約束**新寫／改寫**嘅內容 —— 唔因為「存量未改」就當例外。

**自己生成嘅 markdown 要一致**：skill 唔准「自己用列表、生成嘅文件用表格」。

## 文檔行數限制（v2.8 新增）

**為什麼**：agent 每次觸發 skill 都要把主檔（＋被指標指向嘅子檔）讀落 context；
文檔愈長 → 注意力愈被稀釋、每次觸發嘅成本愈高。行數限制係**寫文件時嘅自律規則**。

- **`SKILL.md`（主檔）**：**150 行**（硬上限）→ 超標必拆子檔：內容留子檔、主檔只留指標
- **單一支援子檔**（`examples.md` / `workflow.md` / …）：**300 行**（硬上限）→ 拆成兩份，或壓成清單
  → **存量例外**（2026-10-28 登記）：`dav-jev-oracle/jev-oracle.md` 361 行、`dav-trust/examples.md` 343 行、
  `dav-jev-oracle/examples.md` 334 行 → 改呢三支要**順手 ratchet 返 ≤300**（只可下唔可上）
- **單一 skill 嘅 context 總量**（主檔 ＋ 全部支援 .md）：**見下面 baseline**（ratchet，只可下唔可上）
  → 先做減法（去重 → 表格化 → 指標化），再考慮拆檔；**只可下唔可上**
- **新增支援檔** → **新增前必先問：可唔可以合併入現有子檔？**
  （淨係新檔 ＋ 新指標 ＝ context 成本淨增）

**ratchet baseline（2026-10-27 現況）** —— 每個 skill 嘅 context 行數上限（只可下唔可上）：

| skill | baseline | 註 |
|---|---|---|
| `dav-jev-oracle` | 1,649 | Jev Oracle ＋ PoC ＋ 4 支探針（2026-10-27 由 dav-developer 拆出）；**已登記例外：超過 1,500 硬上限，ratchet 只可下唔可上**（瘦身另開票）|
| `dav-developer` | 1,208 | 拆分後（拆分前 2,098 行）|
| `dav-submitter` | 1,095 | 併入反省 ＋ retention.md 後（2026-10-28 V03 分流改版後）|
| `dav-trust` | 1,007 | |
| `dav-wiki` | 933 | |
| 其餘 skill | ≤ 700 | |

**點解用 baseline 而唔係一個絕對數字**：本 repo 13 個 skill 合計 ~7,500 行、平均 ~580 行；
一個「全部 ≤700」嘅絕對規則喺內容量面前根本冇人跟得到 → **跟唔到嘅規則 = 假規則**。
→ 改用 **ratchet**：每個 skill 有自己嘅 baseline，**只可下唔可上**；
一個 skill 嘅 context 超過 **1,500 行**（硬上限）→ 必拆成兩個「專注一件事」嘅 skill
（`dav-jev-oracle` 已登記例外，ratchet 只可下唔可上）。
主檔 ≤150 全部守住 ✓；子檔 ≤300 有 **3 支存量例外**（見上面清單，改佢哋要 ratchet 返 ≤300）。

**點樣量**：寫完／改完跑 `find skills/<name> -name '*.md' -type f -exec cat {} + | wc -l`
（主檔 ＋ 全部子檔，**遞迴含嵌套目錄**；baseline 表就係用呢個口徑量）。
主檔改動前另外跑 `wc -l` 預檢（見下面「主檔行數預檢規範」）。

**點解唔用機械探針守**：機械探針守嘅係「文件寫得啱唔啱」，但每加一支探針，
框架層（tests/）就膨脹一次 → 探針自己都係 context ＋ 維護成本。
→ 呢條規則由**寫文件嗰陣（agent）自律**；唔好為咗守一條行數規則再寫一支探針。
（2026-10-27 減法：本 repo 原本嘅 `skill-size-guard`／`framework-weight` 機械守門已刪，
規則改由本章承擔。）

## 主檔行數預檢規範（改 skill 前必跑）

**同源**：AGENTS.md §1.5 的 V03（改動分流：純 markdown 只自查行數上限；代碼／契約／探針先走二審）＋ 本檔的預檢規範

**觸發條件**：任何 skill／SOP 檔案改動前 —— 純 markdown 改動 = V03 文件分支嘅唯一必檢項；
代碼／契約／探針改動 = 走 Reviewer 二審之前嘅預檢

**動作**：
1. 目標 skill 主檔 `wc -l SKILL.md`
2. 若 ≥ 150 → 必先瘦身（主檔 ≤ 130 行再進 §2.2）
3. 若 130-149 → 在設計草案加「行數預警」、避免觸發 150 上限
4. 若 < 130 → 不預警
5. 順手檢支援子檔：`find skills/<name> -name '*.md' -type f -exec wc -l {} + | sort -rn`
   → 任何一個 > 300 行 → 拆檔或壓成表（存量 3 支例外見上面）

**為什麼**：
- 主檔 ≥ 150 行 → 違反本檔「主檔行數上限 150」規範
- 主檔 130-149 → 餘裕不足、未來小變更也可能觸發上限

**例外**：純文字修正（typo / link / 註解）不需預檢

## 探針修改比照 V03（原 V03.6，2026-09-26 新增）

**同源**：AGENTS.md §1.5 的 V03 **代碼分支**（改探針 = 改代碼 → 必走二審）。

`tests/**/*.bats` 的修改**視同規範修改**（新增 / 刪除 / **條件放寬**），必走 V03 Reviewer 二審；
純文字修正（typo / link / 註解 / 訊息文字微調）不觸發。修訂完成後、Reviewer 必附
「`bats tests/<檔>` 跑動輸出」（修改前 fail / 修改後 pass 兩次輸出必貼）。

**「條件放寬」的定義**（符合任一即算）：
1. 讓原本會 fail 的情況改為 pass
2. 檢查門檻變低（例如從「必須綠」改成「綠或黃」）
3. regex 從嚴變寬（例如從 `must contain X` 改成 `must contain X or Y`）

嚴格化（`keep = pass → must pass`）屬規範強化，亦可走 V03 但非必走。
