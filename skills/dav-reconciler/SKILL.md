# Dav Reconciler

## TL;DR

1. **做什麼**：把「用戶當初要什麼」與「這次真的做出什麼」逐條比對，產出**需求對帳表**。
2. **何時觸發**：§2.3 執行段結束、進入 §2.4 反省**之前**（Gate 4.5 需求對帳）。
3. **預設 SOP 路徑**：§2.3 尾段子閘（不是第五道大 Gate；四道大 Gate 定義不動）。
4. **關鍵紀律**：
   - **獨立性**：對帳由**未參與實作**的 subagent 做，不准執行者自己對帳自己
   - **硬門檻**：對帳沒全數對上 → 不得宣告「完成」
   - **只給必要輸入**：不給對帳者實作過程的自述（避免被引導）
5. **必產出物**：
   - 目標專案 `docs/reconcile/<US-ID>-reconcile.md`（需求對帳表）
   - 交付摘要裡的「需求對帳」段（摘要 + 連結）

## 觸發時機

- **開發編程任務執行段完成、進 §2.4 前**
  - 觸發：✅ 必須
- **需求錨點檔存在且本次 US 有 R-ID**
  - 觸發：✅ 觸發前提
- **trust mode 進行中**
  - 觸發：⚠️ 見規則表（不中途停下問用戶）
- **純諮詢 / 一般任務（§2.6）**
  - 觸發：❌ 不觸發
- **存量 US（無需求錨點）**
  - 觸發：❌ 不觸發（無錨點可對）
- **已進 §2.4 反省**
  - 觸發：❌ 太遲了（反省必須建立在已對帳的前提上）

## 流程（5 步）

### Step 1：準備輸入（刻意做少）

- **動作**：組出對帳者要拿的東西 —（a）目標專案的需求錨點檔全文（`docs/req/<US-ID>-requirement.md`）
  （b）本次的最終變更清單（檔案 + diff）（c）該 US 的既有文件（AC 範本、backlog 該列）
- **為什麼不給更多**：執行者的完成宣告與過程自述會把對帳者帶向「照著我說的寫」；對帳的價值在獨立比對
- **產出**：一份給對帳者的輸入包（對話內直接給，不落檔）
- **證據**：對話中可見「我給了什麼、沒給什麼」

### Step 2：交給獨立 subagent 對帳

- **動作**：由**未參與本次實作**的 subagent 依同套 `reconcile-format.md` 產出對帳表
- **為什麼**：自己驗自己 = 沒有驗證；獨立性是這個機制唯一的價值來源
- **產出**：對帳表內容（Markdown 表格）
- **證據**：對帳者身分可辨識（subagent 名稱）+ 對話中貼出原文

### Step 3：檢查完整性（R-ID 覆蓋）

- **動作**：確認對帳表**覆蓋錨點的全部 R-ID**，一條都不能漏
- **為什麼**：漏掉的 R-ID 等於沒對帳；「沒提到」不等於「已實作」
- **產出**：完整性檢查結果（覆蓋率 = 已列 R-ID / 錨點 R-ID 總數）
- **證據**：覆蓋率 100% 才算對帳完成

### Step 4：寫檔 + 回報

- **動作**：把對帳表寫進目標專案 `docs/reconcile/<US-ID>-reconcile.md`；回報結論（全部已實作 / 有部分 / 有未實作）
- **產出**：對帳表檔案 + 結論
- **證據**：檔案存在 + 狀態統計

### Step 5：交給交付摘要（狀態降級）

- **動作**：把對帳結論交給交付摘要產出方；對帳有「部分實作／未實作」時，交付狀態**不得**標「完成」
- **為什麼**：對帳不通過還敢標完成 = 這個機制白做
- **產出**：交付摘要的狀態 + 待補清單
- **證據**：交付摘要內含「需求對帳」段

## 規則 / 例外 / 限制

- 對帳者必須**獨立 subagent**（未參與實作）
  - 例外：環境無 subagent 能力 → 降級為執行者自省對帳
  - 限制：降級時對帳檔與交付摘要**必須**標註「對帳降級（無獨立 subagent）」，且不得宣告對帳通過
- **對帳表必須覆蓋全部 R-ID** — 例外：無；限制：漏一條即對帳不完整；不得視為「無需對帳」
- **狀態值僅 4 種（已實作／部分實作／未實作／已作廢）** — 例外：無；限制：不得自創第 5 種；格式詳見同套 `reconcile-format.md`
- **對帳未全數對上 → 不得標「完成」** — 例外：全部 ❌ 未實作 → 可標「未完成」；限制：其餘只能標「部分完成」並列出待補項
- **錨點的需求句數 = 0 → 對帳失敗** — 例外：無；限制：不得視為「無需對帳」；須回報「錨點無需求句」由人補正
- **給對帳者的輸入不含實作自述** — 例外：無；限制：給了自述就失去獨立性
- **trust mode 進行中不中途停下問用戶** — 例外：用戶叫停時立即收斂；限制：對帳結果照常產出，缺口記入 trust-log 代答 + need-you-help 待回覆
- **不適用於沒有需求錨點的存量任務** — 例外：用戶明確要求時可手動補錨點；限制：手動補的錨點須標明來源為「代擬」

## 工具：文件漂移檢查（隨本 skill 一起安裝）

> 目標專案安裝 tree_monstor 後，本 skill 的 `scripts/check-doc-drift.py` 會跟著到位，
> 專案可自己跑「文件漂移檢查」（D1..D8）把「同一件事多份文件各說各話」擋在 CI。

### 怎麼跑

```bash
# 目標專案的專案根目錄下執行（--root 預設＝目前目錄）

python3 <安裝後的 skill 目錄>/scripts/check-doc-drift.py --root .
```

- **`--root <專案根>`**
  - 說明：要檢查的專案根目錄（預設：目前目錄）
- **`--whitelist <檔>`**
  - 說明：白名單檔（預設：`<root>/docs/ci/drift-whitelist.txt`）
- **`--from-date YYYY-MM-DD`**
  - 說明：交付摘要檢查的生效日（回溯舊交付會大量假紅）
- **`--require-window-checks`**
  - 說明：
    **fail-closed 嚴格模式**：`docs/deliverable/` 存在時，窗內必須有交付摘要，且至少要有一支引用得到 `docs/req/` 錨點（否則 D4/D8 的檢查件數為 0＝硬門檻靜默失效）→
    rc=1。本 repo 的 `scripts/ci/check-doc-drift.sh` 在未指定 `--root` 時會**自動**加上它；帶 `--root` 即視為外部專案、只印 `WARNING`（可攜語意）

**rc 契約**：`0` 無違規（含全部被白名單豁免）｜`1` 有違規｜`2` 用法 / 環境錯誤（fail-closed）

### 目標專案要先準備什麼

1. `docs/backlog.md`（狀態欄位是 D1 的比對基準；本專案以 backlog.md 的「狀態定義」為單一來源）
2. `docs/ci/drift-whitelist.txt`（白名單，每行 `<類>#<鍵>#<理由>`；**理由不可為空**，全類豁免 `<類>#*` 會被 rc=2 擋下）

### CI 範例

```yaml
# 方式 A（推薦）：用 wrapper —— 未帶 --root 時自動開嚴格模式（本 repo 的做法）

- name: Verify no document drift
  run: bash scripts/ci/check-doc-drift.sh --from-date 2026-10-26

# 方式 B：直接呼叫 python —— 這時**必須自己**帶 --require-window-checks，
#         否則等同只拿 warning 模式，fail-closed 不會生效
- name: Verify no document drift
  run: python3 <skill 目錄>/scripts/check-doc-drift.py --root . --from-date 2026-10-26 --require-window-checks
```

## Gate 定義（本節是 single source 之一；定義本體＝`docs/sop/handbook/2.3-execution.md` 的「Gate 4.5 需求對帳」段）

> **進本 Gate 時必須在對話引用下表的 `mandatory_phrase`；不引用＝視為 gate 未觸發**（屬「偽裝通過」，依 SOP 的違規回報規則處理）。
### Gate 4.5 需求對帳（§2.3 尾段子閘）

> Gate 4.5 是**內嵌子閘**，不進 `docs/sop/gates.json`（該檔的 gate `id` 受 schema 限制，
> 只允許整數編號的四大 Gate）。它的定義本體在 `docs/sop/handbook/2.3-execution.md` 的
> 「Gate 4.5 需求對帳」段（本節為該段的 skill 端鏡像；鎖兩邊一致嘅探針已於 2026-10-27 減法刪走 → 兩邊要人手同步）。

- **pass_criteria**
  - 內容：① 對帳表覆蓋錨點的全部 R-ID（覆蓋率 100%）② 由未參與實作的獨立 subagent 執行（降級須標註）③ 對帳結果帶入交付摘要，且交付狀態與對帳結果一致
- **required_evidence**
  - 內容：① 需求對帳表（落在目標專案的 reconcile 目錄）② 未參與實作的 subagent 對帳原文回傳 ③ 交付摘要的「需求對帳」段與覆蓋率
- **fail_action**
  - 內容：不可進入 §2.4 反省
- **mandatory_phrase**
  - 內容：依 §2.3 規範，Gate 4.5 (需求對帳) 需要：對帳表覆蓋全部 R-ID + 獨立 subagent 對帳原文 + 交付狀態與對帳結果一致，並在對話貼出對帳表與覆蓋率。
