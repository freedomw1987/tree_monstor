# Dav Technical Proposal — Reference

> 本檔為 dav-technical-proposal 的參考資料附件，按需查閱。主檔在 `SKILL.md`；交付與 Word 產出在 `delivery.md`；圖在 `diagrams.md`。

## §1 交付定位、命名與語言

- **定位** — 客戶交付型技術方案書（Technical Proposal）：對外文件，唔係內部設計文件；行文用「我方／貴方」或「服務提供方／客戶方」，全份統一
- **產出兩版**
  - 工作版：含「待確認清單」＋內部註記 → `docs/proposal/<client>-<project>-<year>-technical-proposal.md`
  - 交付版：淨稿（剔走待確認、內部註記、括號位）→ `docs/proposal/<client>-<project>-<year>-technical-proposal-delivery.md`
- **命名** — `<client>-<project>-<year>`，例：`wynn-ai-muse-2026-technical-proposal.md`
- **語言** — 跟目標客戶／報價文件語言；用戶可指定；中文內文一律書面語（§9）；對話同提問可用口語
- **圖檔** — 需圖檔（png／svg）或互動式架構圖（html）時，放 `docs/proposal/assets/<client>-<project>/`；檔名同方案書內嘅「圖 N」對應
- **章節標題** — 保留客戶／投標慣用英文標題 ＋ 中文對照，例：`## 1. Project Background（項目背景）`；**交付版若全文改用單一語言，就去掉括號對照**
- **投標文件帶入章節** — 客戶投標文件通常要求公司簡介／組織架構／認證／案例／客戶名單；呢啲章節用招標原文（唔翻譯、唔改寫），放喺方案書指定位置

## §2 核心 9 維度（必問；每維度標明落點章節）

1. **現況與痛點** → 1.1 Current Situation Analysis — 現行做法、瓶頸、痛點（能量化就量化）
2. **建設目標與成功標準** → 1.2 Construction Object — 目標、建成後嘅狀態、可驗證嘅成功指標
3. **範圍與排除項** → 1.3 Project Scope ／ 1.5 Out of Scope — 交付邊啲、明確唔做邊啲
4. **假設與約束** → 1.4 Assumption — 期限、預算、既有系統限制、第三方授權與費用歸屬
5. **技術架構與整合對象** → 2.1 System Technical Architecture — 系統分層、資料流、對外接口、需整合嘅外部系統
6. **功能模組與用戶介面** → 2.2.1 User Surface ／ 2.2.2 Functional Modules — 有邊幾類使用者、每個模組做咩
7. **技術棧與非功能需求** → 2.2.3 Technical Stack and Framework ／ 2.3 Non Functional Requirement — 效能、可用性、安全、可擴展、合規
8. **部署環境與基礎設施** → 2.4 Infrastructure Requirement — on-prem 定 cloud、資源規格、網絡、第三方服務
9. **團隊組織與排期** → 3.1 Project Organization Structure ／ 3.2 Project Tentative Schedule — 角色分工、milestone、暫定工期

- **提問方式** — 每輪 1 題、2-4 個選項、⭐ 推薦放第 1；答案即時落對應章節（唔好問完先記）
- **收斂提示** — 講「要智能啲」→ 追問「做完之後使用者少做咩步驟」；講「系統要快」→ 追問「幾多併發、多大數據量、容忍幾多秒」

## §3 觸發式補充維度（觸發咗要問；答案落指定章節）

- **畫面與原型** → 2.5 — 有無現成原型或畫面可以截圖；邊個負責補圖
- **數據遷移** → 2.6 — 有無既有系統、舊數據量與品質、停機窗口、對賬方式
- **第三方與授權** → 1.4 ／ 2.4 — 授權來源、版本、費用由邊個負責、有無採購週期
- **合規與私隱** → 2.3 — 數據落地、跨境限制、行業監管、稽核要求
- **語言與地區** → 1.1 ／ 2.2.1 — 多語介面、部署地區、時區
- **待確認問題** — 答唔到嘅問題唔自己作

## §4 成熟度評估（寫之前必跑）

- **涵蓋率** — 0：只講 1 維度｜1：講 2-3 維度｜2：核心 9 維度齊｜3：核心 9 ＋ 觸發式補充 ≥3 條
- **清晰度** — 0：抽象｜1：部分具體｜2：全部具體但無量度｜3：全部具體 ＋ 可量度 ＋ 可觀察
- **可行性** — 0：未考慮技術風險｜1：有想過未驗證｜2：有把握或已驗證｜3：有 PoC 或現成方案
- **規則** — 3 維度都 ≥2 → 可寫；任一 = 0 → 必須繼續問；任一 = 1 → 可寫但要標 ⚠️「需求成熟度不足」
- **維度同章節對齊** — 背景、假設、排除項唔變成功能模組；只有「要交付嘅能力」先寫入 2.2.2

## §5 章節骨架與寫法

- **三大塊骨架必備** — Project Background／Technical Solution／Implementation Plan；缺任何一大塊 → 唔算完成稿
- **骨架可擴充** — 投標文件要求嘅章節（公司簡介／案例／認證）插喺指定位置，插完要重編所有章節號 ＋ 圖號 ＋ 正文交叉引用（驗證方法 → `delivery.md` §3）
- **1.1 Current Situation Analysis** — 現況描述 ＋ 瓶頸 ＋ 影響（3-5 句 ＋ 列表）；唔好只寫「系統舊」
- **1.2 Construction Object** — 目標陳述 ＋ 建成後狀態 ＋ 可驗證成功指標
- **1.3 Project Scope** — 交付範圍清單（按 2.2.2 模組對齊，兩邊可互相對照）
- **1.4 Assumption** — 三類必寫：環境與資源／範圍與計算基準／商業與技術假設；另加通用條款「任何未於本文件列明之服務或功能均不包含於本次交付範圍」
- **1.5 Out of Scope** — 明確不做項（至少 2-3 條）
- **2.1 System Technical Architecture** — 分層（前端／後端／整合／基建）＋ 資料流 ＋ 對外接口 ＋ **責任邊界段**（邊個提供邊啲、邊啲喺邊個平台納管）
  - **附系統架構圖**（`graph TB`；見 `diagrams.md`）；唔用 ASCII 框圖
- **2.2.1 User Surface** — 使用者類型 ＋ 各自入口與裝置 ＋ 主要操作路徑；可附主要操作流程圖（方向按可讀性定）
- **2.2.2 Functional Modules** — 每個模組寫「做咩 ＋ 包含咩功能 ＋ 對應使用者角色」；模組名同 1.3 範圍對得上
- **2.2.3 Technical Stack and Framework** — 每項技術寫「點解揀佢 ＋ 限制條件」；冇理由嘅技術唔好列
- **2.3 Non Functional Requirement** — 效能／可用性／安全／可擴展／合規；可量度就寫數字，未確認就標「待確認」；**基準數據要同時寫明限制**（測試條件、唔構成 SLA、最終值點定）
- **2.4 Infrastructure Requirement** — 環境類型、資源規格（伺服器角色／最低資源用表格）、網絡與安全要求、第三方服務依賴、邊個提供；**附基礎設施拓撲圖**
- **2.6.3 Migration Process** — 遷移步驟 ＋ 每步產出 ＋ 驗證點；**附遷移流程圖**（要講對賬時序先用 `sequenceDiagram`）
- **3.1 Project Organization Structure** — 角色 ＋ 職責（用戶唔要求就唔加投入方式／模組對應欄）
- **3.2 Project Tentative Schedule** — Phase ＋ milestone ＋ 暫定工期；必寫「暫定」並註明依賴前提
- **表格使用（敘述用列表、可比較用表格）** — 敘述性內容（背景、目標、假設、Out of Scope、原則、限制、段落說明）一律用列表；同一組資料只要有多個項目且需要同列比較，就用表格呈現
  - **判準** — 問「要逐項讀落去」定「要橫向對照？」；前者用列表，後者用表格
  - **常見適用位置** — 成功指標、模組與授權行項、術語表、分層與組件、模組對照、非功能指標、環境與資源規格、截圖清單、遷移步驟／風險／排期、組織角色、排期、待確認清單
  - **表格寫法** — 每欄標題要自我解釋（唔用「欄 1／A」）；欄數 ≤6；每格內容精簡，長段落留喺列表；同一組資料唔好喺同一份文件入面表格同列表混用
  - **唔好用表格做** — 欄位定義、規則清單、原則說明、單一長段落敘述（呢啲係列表嘅活）

## §6 條件式章節規則

- **2.5 System Function Screenshots**
  - 有原型或現成畫面 → 每個介面一張截圖 ＋ 一句功能說明 ＋ 圖檔路徑（圖檔唔喺本 repo 內就寫存放位置）
  - 冇來源 → 唔准自己生成假圖；寫「待補截圖清單」（介面清單、截圖來源、補圖責任方、補齊期限）
- **2.6 Data Migration**（只喺涉及既有系統或舊數據時出現）
  - 出 5 個小節：2.6.1 Strategy／2.6.2 Scope／2.6.3 Process／2.6.4 Risk and Assumption／2.6.5 Schedule
  - 唔涉及 → 整節標「不適用（本次交付不涉及既有數據遷移）」並講原因，唔准留空
- **通用** — 唔准為咗「睇落完整」而虛構章節內容；冇內容就講明點解冇

## §7 自足性與術語表

- **自足性（成品唔靠引用）** — 方案書係客戶單獨一份就可以讀嘅文件；所有細節（範圍、流程、參數、限制、角色、數據流、數量）必須喺正文寫出
  - **禁止嘅寫法** — 「詳見《需求文檔》」「參見附件 1」「見 PRD 第 3 章」「如前所述」「另一份文件有描述」→ 改寫成正文內容
  - **同一份文件內互引可以** — 例：「見 2.3 效能條款」；但唔准叫人離開份文件去另一份文件搵
  - **例外（可以引，但要寫重點）** — 外部標準或法規（例：ISO 27001、GDPR、PCI DSS）：寫明標準名 ＋ 本方案要滿足嘅具體要求，唔准淨寫標準名
  - **圖與截圖** — 圖要自帶圖例同節點職責；唔准用「見截圖」代替文字描述
- **術語表（Glossary）** — 交付版必備：列出方案書內全部專有名詞縮寫
  - **條目格式** — `- **縮寫（英文全稱，中文名）**：<本方案書內嘅具體所指，一句>`
  - **收錄範圍** — 技術縮寫（API、RAG、ERP、SLA…）、工具／模型／框架名（TEI、vLLM、bge-m3…）、產品／方案專有名詞、客戶內部系統或部門簡稱、本文件自訂術語
  - **首次出現規則** — 每個縮寫喺正文第一次出現要寫全稱 ＋ 縮寫，之後先用縮寫；**工具／模型名密集時可用「章節開頭一次過展開」**（一行列出本章用到的全稱），避免正文每處重覆
  - **每條都要有用到** — 交稿前逐條核對：術語表有、正文冇 → 刪條目或補正文；正文有、術語表冇 → 補條目
  - **唔收錄** — 通用英文詞（user、data）、行業通用且無歧義嘅名詞

## §8 書面語規範（中文內文）

- **原則** — 繁體中文書面語；完整句式、名詞化、可驗證；對話同提問不受限
- **禁用字眼對照（口語 → 書面語）**
  - 搞／整／做咗 → 開發／建置／完成；有／冇 → 包含／不包含、提供／未提供
  - 嘅 → 的；喺度 → 於；呢個／嗰個 → 本項／該項；咁／咁樣 → 因此／如此
  - 啲 → 若干；唔 → 不；仲要 → 另需；要點 → 如何
  - 交返／搞掂 → 交付／完成並通過驗收；頂住／handle → 支援／處理；睇／諗 → 檢視／評估
- **允許保留** — 產品名、專有名詞、英文術語（on-premise、API、RAG、mandays、PoC）；客戶慣用名照客戶寫法
- **語氣** — 陳述式、客觀、對外一致；避免第一人稱「我哋」、宣傳形容詞
- **禁空泛詞** — 高性能／現代化／強化／完善／提升體驗 → 換成可驗證描述（例：「查詢回應時間 ≤2 秒（資料量 100 萬筆）」）

## §9 內容自查清單（交付前逐項過）

- 三大章節齊，章節編號同模板一致；有插章節時重編後嘅編號連續、無重複
- 1.1-1.6 每節有實質內容；1.4 Assumption 有三類 ＋ 未列明事項通用條款；1.5 至少 2-3 條；術語表已列齊
- 2.1 有分層 ＋ 資料流 ＋ 責任邊界；2.2.1 有使用者與入口；2.2.2 每模組有「做咩 ＋ 包含咩 ＋ 角色」
- 2.2.3 同 2.3 每項都寫「點解 ＋ 限制」；基準數據附測試條件同限制；無量度者已標待確認
- 2.4 講明邊個提供環境與資源（伺服器角色／最低資源用表格）
- 架構圖類（2.1／2.4／2.6.3）有圖；圖種同章節對得上；互動圖與 Mermaid 一致
- 圖內節點名同正文一致；每張圖有「圖 N — 名稱」標題；已過 Mermaid 語法防錯
- 2.5 同 2.6 按 §6 規則處理（有待補清單或「不適用 ＋ 原因」）
- 3.1 角色與職責齊；3.2 有 phase／milestone／暫定工期同前提
- 中文內文逐句書面語（對照 §8 禁用字眼）；專有名詞保留英文
- 成品自足：冇「詳見其他文件／參見附件／如前所述」式引用；所有細節直接寫喺正文
- 術語表列齊全部專有名詞縮寫，每條正文都有用到，每個縮寫正文首次出現有全稱
- 產出物用列表為主；資料表符合 §5 表格規則（欄標題自我解釋、欄數 ≤6、每格精簡）
