# PPTX Slim

## TL;DR

1. **做什麼**：把「媒體佔 90%+ 體積」的 PPTX **就地減重**（實測 2.9 GB → 418 MB，−86%），**不是** zip 壓縮、**不是**重寫 PPT。
2. **何時觸發**：用戶說檔太大／開唔到／傳唔到／上載失敗，而且 media 佔比 > 50% 的 .pptx。
3. **預設 SOP 路徑**：§2.6 一般任務（輕量）；若同時要改 PPT 結構（加頁、改動畫）才升級完整 SOP。
4. **關鍵紀律**：
   - 原檔零改動，永遠寫新檔；**容器／檔名／時長不變**
   - 非媒體 entry **逐 byte 原樣**（XML 一改，動畫、時序、書籤就散）
   - 壓完比原檔大 → 保留原檔（實測 17 支影片有 1 支如此）
   - 圖片預設**無損**（PNG 重壓／TIFF deflate，像素逐點相同）；只碰 Pillow 保證得了的格式，其餘明示 SKIP
   - 四關驗證（CRC／entry 齊全且非媒體 byte 相同／rels 零斷鏈／時長漂移）缺一不可；有換圖片再加畫質關；再加人工「播放器實開」最後一關
5. **必產出物**：新檔 `<原名>_<profile>.pptx` + 媒體偵察表 + 轉碼前後對照表 + 四關驗證輸出。

## 觸發時機

| 情境 | 觸發 |
|------|------|
| PPTX 過大（> 100 MB 或超過上載／郵件上限），且媒體佔比明顯 | ✅ 必須 |
| 已試過 zip／另存新檔仍然太大，且必須保住頁面、動畫、時序 | ✅ 必須 |
| 純 zip 壓縮（.zip 交付）、壓「PPT 以外」的散裝圖片資料夾、加密或損壞檔救援、非 .pptx 容器（docx／keynote／PDF）| ❌ 不觸發 |
| 檔太大而體積主要來自圖片（影片只佔少數），但**仍舊要保住簡報結構** | ✅ 觸發（只跑流程 7 的無損圖片管線，不動影片）|
| 同一次要改內容（加頁、換圖、改動畫）| 🟡 先完成內容修改，再跑本 skill 縮檔 |

## 流程（7 步）

| Step | 動作 | 為什麼 | 產出 | 證據 |
|------|------|--------|------|------|
| 1 偵察 | 跑 `scripts/pptx-probe.py`：列 media 佔比、非媒體體積、每支影片的解析度／時長／bitrate | 先知道體積來源同「最貴的幾支」，否則盲壓 | 偵察表（分類彙總 + Top 20）| probe 原始輸出 |
| 2 定 profile | 給 2–3 個選項（如 1080p CRF24／720p CRF28／只壓 Top 3）＋標明推薦 | 畫質與體積是取捨，必須用戶決定 | 選定 profile | 對話一句「用 profile X」 |
| 3 轉碼 | 跑 `scripts/pptx-shrink-media.py`（同容器、同檔名、壓完更大自動保留原檔）| 媒體就是 90%+ 體積來源 | `encoded/` 目錄 + encode log | 每支 before→after 大小表 |
| 4 重打包 | 跑 `scripts/pptx-repack.py`：開新檔、只換 media entry、其他 entry 逐 byte 複製 | XML／rels 動一下就會散動畫與時序 | 新 .pptx | `N/N entries written, M replaced` |
| 5 驗證 | 跑 `scripts/pptx-verify.py`：CRC｜entry 齊全 + 非媒體 byte 相同｜rels 零斷鏈｜時長漂移 | 靜默壞檔比大檔更貴：開會才發現就太遲 | 驗證報告（四關全綠）| verify 輸出 + 播放器實開結果 |
| 6 交件 | 命名 `<原名>_<profile>.pptx`；用完對比原檔 md5 | 原檔可回溯，出錯可零成本重來 | 最終檔 | `ls -l` 前後對照 |
| 7 加碼（可選）| 影片壓完仍不夠小時：跑 `scripts/pptx-shrink-images.py`（無損優先）或對影片用 `--only` 精準打擊 | 圖片常是「第二大來源」（實測 139 MiB 含 29 MiB TIFF）| `image-log.tsv` + 更新的對照表 | 同上四關重跑，並加 `--media-dir` 交叉核對與 `--image-mode` 畫質關 |

## 規則 / 例外 / 限制

| 規則 | 例外 | 限制 |
|------|------|------|
| 原檔零改動，只寫新檔 | 用戶明示可覆蓋原檔 | 需預留與原檔同級的磁碟空間 |
| 檔名、容器格式、時長不變 | — | 換容器（mp4→webm）會斷 rels，絕對不做 |
| 非媒體 entry 逐 byte 原樣 | — | 不可順手清「看起來沒用」的 media，會斷 rels |
| 壓完更大就保留原檔 | 用戶堅持要統一參數 | 縮圖級小檔常見（實測 media1 就是）|
| 四關驗證：CRC／entry 齊全且非媒體 byte 相同／rels 零斷鏈／時長漂移 | 無播放器環境 → 四關照跑，但明示「未做人工實開」並降級宣告風險 | 缺任一關不得宣稱完成（人工實開算最後一關）|
| 一次只換一個變數（媒體）| — | 不可同時改 XML 或頁面結構 |
| 圖片預設無損，有損必須明示 | 用戶明示接受掉畫質 | PSNR 只在 RGB 空間量（alpha 是有損近似）；要 alpha 也無損走 `--mode lossless` |
| 圖片預設無損（PNG 重壓／TIFF deflate），像素逐點自證 | 無損省不夠 → 才用 `--mode lossy`（長邊 + PSNR 門檻）| 無損只碰 PNG／TIFF 8-bit；JPEG、16-bit、GIF、EMF 一律 SKIP 並說原因；省幅要用**未壓縮媒體總量**估（entry 在 zip 內本來就 deflate 過的，整包幾乎不變）|
| 有換圖片就要加畫質關（`--image-mode`）| 只換影片 → 不必（這一關不適用）；deck 只有向量圖（.svg/.emf/.wmf）→ 沒有可比的光柵圖，明示不適用 | 無損要求像素完全相同；有損要求尺寸上限 + PSNR 不低於門檻；**逐 byte 相同的圖＝刻意保留（SKIP／KEPT／`--min-bytes`），不計入長邊上限**；PSNR 在縮圖尺寸比（不把縮圖放大回母帶）|
| 依賴 ffmpeg + python3 + python-pptx + Pillow | 缺工具 → 停下問用戶是否安裝，不靜默降級 | 壓影片只需 ffmpeg；壓圖片那條路才需要 Pillow（不碰圖片的任務不該被它擋住）|

**常見坑**：長邊封頂（1920）只縮長邊、短邊用 `-2` 自動偶數，避免豎屏被過度縮小；有 rotation metadata 的影片要先轉正再縮。
